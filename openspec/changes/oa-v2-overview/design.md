# Design — OA 2.0 总纲（批次拆分、模块边界与技术选型）

> 本设计只覆盖**跨批次**的架构决策。批次内的详细设计见 `doc/2.0/2.0-PRD-OA升级开发.md` 第 8/9/10 章，
> 以及各批次变更集自己的 `design.md`。动机见 `proposal.md` — Why。

## Context

- **现状（源码级）**：见 `doc/2.0/RuoYi现状勘察.md`。与本设计相关的四条：
  1. 模板新增页是 5 个纵向分段（`UI/views/workflow/template/add.vue:1-45`），简化流程设计器是独立菜单
     （`UI/router/index.js:161-162`），二者**无任何自动绑定**，`def_key` 靠人工填（`index.vue:80-89`）；
  2. `submitScope` 在全仓零命中，发起页只过滤 `del_flag`/`enable_flag`（`TemplateMapper.xml:148-157`）；
  3. 内置打印模板是**全局唯一一套**且被前端强制关闭签批栏（`PrintServiceImpl.java:391-402,466`、`print/index.vue:182-200`）；
  4. `updateTemplate` **换新 ID**（`TemplateServiceImpl.java:154-176`）—— 所有 `template_id` 外键表在编辑后失联。
- **参考实现**：`doc/2.0/参考仓库-CTMS-移植清单.md`。39 表 / 99 权限点 / ~231 端点 / 后端 9,385 行 /
  前端 35 视图 + 15 组件 10,358 行；Python FastAPI + SQLAlchemy + SQLite / Vue3 + Element Plus。
- **约束**：环境为**本机 Windows + JDK 11（toolchains）**（`DEV-ENV.md`）；后端运行必须用
  `D:\Program Files\Java\jdk-11\bin\java.exe`；前端必须 `npm.cmd run dev`；SQL 有"基线 + 增量"双轨。

## Goals / Non-Goals

**Goals**

- 把 2.0 拆成**四个可独立评审、独立验收的批次**，明确批次间的依赖与关键路径。
- 为"搬进来的业务系统"确定**落点（新模块 or 既有模块）**与**复用边界**，避免第二套平台。
- 把三条已知会造成数据损坏的隐性依赖（换 ID、表单版本化、发布无补偿）在**动功能之前**先解决。

**Non-Goals**

- 不在本设计内确定批次内的表结构、接口签名、页面交互（属于各批次设计）。
- 不改动 Flowable 引擎配置、不改动既有认证链、不做技术栈升级（Vue2 → Vue3）。
- 不设计合同/采购/销售/库存的**业务规则**（业务规则真源是参考仓库已冻结的 BR / AC-V2 体系）。

## Decisions

### D1 以"批次"而非"一次性大爆炸"推进，且 B1+B2 与 B3+B4 分离

- **选择**：B1（表单与流程设计）、B2（打印模板）为一批次线；B3（合同台账）、B4（采购/销售/库存）为另一批次线。
- **理由**：B1/B2 与既有代码同源，改动集中在 `ruoyi-template` / `ruoyi-workflow`，风险可控、周期短；
  B3/B4 是"把一个已在 UAT 的独立系统搬进来"，后端与前端都是 XL 量级，且必须先冻结数据范围口径与并发方案。
  两者的**验收节奏、参与人、风险面完全不同**，强行合批会让 B1/B2 被 B3/B4 的排期拖住。
- **备选**：(a) 一次性全量——被否，B3/B4 的工期会让 B1/B2 的快速收益消失；
  (b) 先做 B3/B4——被否，B2 的"按单据类型选内置模板"正是 B3/B4 单据打印的前置。

### D2 移植落点为**新建后端模块 `ruoyi-ctms`** + 前端 `views/ctms/**`

- **选择**：合同/主数据/单据/库存/过账等新代码放一个新 Maven 模块 `ruoyi-ctms`（与 `ruoyi-template`、`ruoyi-workflow` 同级），
  前端放 `src/views/ctms/**` + `src/api/ctms/**`。
- **理由**：① 与既有 `ruoyi-workflow`（流程/打印/签名）、`ruoyi-template`（模板）职责不混；
  ② 39 张表与 231 个端点放进既有模块会让模块边界失效；③ 未来若要下线或拆分这块业务，边界清晰。
- **备选**：(a) 塞进 `ruoyi-workflow`——被否，职责污染且模块已 28 个； (b) 每个域一个模块（4 个）——被否，
  单据与库存共用 `DocMixin`/过账服务，拆开会产生跨模块循环依赖。

### D3 `t_template` 是主、流程是从：模板持有对流程的强引用

- **选择**：`t_template` 增 `simple_flow_id` / `flow_mode`，发布时由后端**回写** `def_key`；
  `defKey` 规则为 `tpl_` + 模板 id 前 8 位。
- **理由**：现状是"人手抄字符串"，两个 `def_key` 一旦不一致就是静默错配；强引用让"模板 → 流程"可校验、可级联。
  用 id 派生 `defKey` 而不是用模板名，是为了避免重名与非法字符。
- **备选**：(a) 只回写 `def_key` 不加 `simple_flow_id`——被否，无法表达"流程还是草稿、尚未发布"；
  (b) 用模板名派生 `defKey`——被否，中文名不适合做流程标识且有重名风险；
  (c) 页签 3 只做"选择已有流程"——被否，不符合用户"移到这里、自动绑定"的原话。

### D4 保存顺序：先模板拿 id → 再流程 → 发布时回写

- **选择**：`① 保存模板（upsert，拿 id）→ ② 由 templateId 取/建流程草稿 → ③ 发布时在同一后端事务里部署并回写`。
- **理由**：`defKey` 由模板 id 派生，所以**必须先有模板 id**；而流程草稿可以早于发布存在。
- **备选**：先流程后模板——被否，`defKey` 就无法由模板 id 派生，且模板的 `def_key` 是 `NOT NULL`，
  需要临时 key 或放宽约束（治标不治本）。

### D5 先在 B1 内修掉 `updateTemplate` 的换 ID 语义（原地 UPDATE）

- **选择**：`updateTemplate` 改为原地 UPDATE 同一行（id 不变）；如需版本快照另建 `t_template_history`。
- **理由**：页签 3 的回写、5 张 `template_id` 外键表、前端提交后不取新 id，这三件事**任何一个**放在换 ID 的语义上都会坏；
  这是 B1 的前置条件而不是可选优化。
- **备选**：(a) 保留换 ID、编辑后级联搬迁子表——被否，每加一张子表都要记得改，长期必然漏；
  (b) 不动——被否，会污染 2.0 新增的 4 张表。
- **代价**：需要一次存量归并迁移（把 `del_flag='1'` 的旧行与新行的子表引用统一到启用行），
  迁移前必须先输出**影响行数报告**。

### D6 内置打印模板用"模板上的 key"，不用"预置数据行"

- **选择**：`t_template` 增 `builtin_print_key varchar(32) DEFAULT 'contract'`；后端 `builtinTemplate(key)` 返回标题 + 版式。
- **理由**：① 复用现有优先级链（显式 `printTplId` > 单据模板下启用行 > 内置）不变；
  ② 不引入 seed 数据，避免"单据模板还没建时没有 `template_id` 可挂"的问题；
  ③ 改动集中在 8 个代码点（见 PRD 6.2）。
- **备选**：(a) 预置 3~4 条 `t_template_print_template` 数据行——被否，与 `template_id` 的时序耦合；
  (b) 用 `t_template.type`（模板分类）映射内置 key——被否，分类是业务分组，与打印版式不是一对一。
- **必须同时修**：前端 `isBuiltinTpl` 强制关闭签批栏（`print/index.vue:182-200`）。否则资金审批单**配不出来**。

### D7 参考实现的"应用层强制"在 MySQL 侧改回数据库约束

- **选择**：参考实现里 17 类靠应用层保证的 `NOT NULL`/外键（因 SQLite `ALTER TABLE ADD COLUMN` 的限制），
  在 MySQL DDL 中恢复为列的 `NOT NULL` 与真实 FK。
- **理由**：约束能落到数据库才是可靠的；应用层强制在**导入/迁移/直连脚本**路径上是无效的。
- **代价**：必须逐条确认写入路径（尤其是"导入"与"历史档案迁移"两条旁路），否则运行期约束爆炸。
- **备选**：原样保留可空——被否，等于把一个已知缺陷一并搬进来（`proposal.md` 的门禁规格明确禁止）。

### D8 单据审批保留单级状态机，不接入 Flowable

- **选择**：参考实现的 `draft → submitted → approved`（库存类 `approved` 即终态）保持单级；
  可选地把它映射到 OA 的待办入口以便统一。
- **理由**：参考实现的业务口径就是单级审核（其需求文档明确"不做多级"）。
  接 Flowable 会把状态机、待办来源、办结口径、权限判定**全部推倒重来**，收益为零、风险极高。
- **备选**：全部走 Flowable——被否（见上）。若未来确需多级，再单独立项。

### D9 过账必须显式加锁 + 事务；金额必须"先舍入再汇总"

- **选择**：过账/红冲/下推走 `@Transactional(rollbackFor = Exception.class)` + 行锁（`SELECT ... FOR UPDATE`）；
  `stocks` 建唯一索引并捕获重复键重试；金额全程 `BigDecimal` 且**行金额先舍入到分，再求和**。
- **理由**：参考实现靠"服务层不 commit + SQLite WAL 串行写 + 路由层一次提交"掩盖了并发，
  其自身注释已预告"切换数据库时要加行锁"；本金精度口径（先舍入再汇总）写在其业务规则里，
  若 Java 侧先汇总再舍入会产生 1 分钱差异，导致导出/打印/对账三方不一致。
- **备选**：依赖数据库默认隔离级别——被否，MySQL 默认 RR 下"先查后插结存行"仍会双插。

### D10 数据范围自建，不复用 `@DataScope`

- **选择**：业务表的数据范围判定按 `dept_id` + `sys_dept.ancestors` 自建（参照既有 `DocViewGuard` +
  四路 union 的范式），并把"本人/本部门/本部门及下级/全部"四档与"多角色取并集"写进代码注释与测试。
- **理由**：`@DataScope` 只用在系统模块的 5 处，与业务单表无关；参考实现的 `SELF` 用 `created_by`、
  `DEPT` 用 `org_id` + 物化路径 LIKE，而 OA 没有 `org_id` 概念、默认按 `user_id`/`dept_id`。
  两套语义**不等价**，直接套用会越权或"该看的看不到"。
- **备选**：给业务表强行套 `@DataScope`——被否，语义不匹配且会误隔离主数据。

## Risks / Trade-offs

- [换 ID 迁移会改动存量数据] → 迁移脚本先出**影响行数报告**；在 B1 的 S0 阶段就用生产库副本演练一次；
  保留回滚脚本（按迁移前快照恢复 5 张子表的 `template_id`）。
- [表单有两条渲染路径 + 动态表单是版本化的] → 新增控件严格按 11 处清单落地；改表单后**显式**把模板指向新版本；
  在门禁中加"设计器能拖 / 拟稿能填 / 审批能看 / 打印能出"四态回归。
- [前端全量重写规模不可控] → 用参考实现的 Playwright 用例作为**行为基线**改写；先做 7 个重头页；
  把"Element Plus → Element UI 的静默差异"（`value-format` 日期格式等）写成 grep 门禁。
- [D7 恢复数据库约束可能在旧数据上失败] → 迁移脚本分两段：先跑数据体检（找出违例行），再执行 DDL；
  违例行输出清单而不是直接失败。
- [B1/B2 与 B3/B4 分线的沟通成本] → 两批次的 `REQ-*` 域分离（`FORM/DESIGN/PRINT/PERM` vs `CTMS/PUR/SAL/STK`），
  共用的只有平台能力；门禁规格（`platform/delivery-gate`）作为共同约束。

## Migration Plan

1. **准备**：备份 `rad_oa`；在副本上先跑一次全量迁移演练。
2. **平台前置（B1 之前）**：`updateTemplate` 改原地 UPDATE；存量归并迁移（输出影响行数）；
   `table.sql` 之外的增量 SQL 编排为 `sql/初始化-全部.sql`。
3. **B1/B2**：增列与 4 张新表 → 后端接口 → 前端四页签与内嵌设计器 → 打印内置版式 → 回归。
4. **B3/B4**：39 表 DDL（含约束回补）→ 后端模块 `ruoyi-ctms` → 前端 `views/ctms/**` → 权限点 SQL → 回归。
5. **回滚**：
   - 代码回滚：三个仓库各自回退到发布前的 commit（`DEV-ENV.md` 记录了三仓库的 git 基线）。
   - 数据回滚：新增表可直接 `DROP`；`t_template` 的新增列可保留（默认值即旧行为）；
     唯一需要反向脚本的是第 2 步的**归并迁移**（保留迁移前快照表 `t_template_migrate_backup`）。
6. **验证顺序**（与 `platform/delivery-gate` 一致）：静态审计 → 越权脚本 → 签名脚本 → 流程回归 →
   批次新增回归脚本 → 人工 UAT 清单。
