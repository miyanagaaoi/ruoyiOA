# Spec Delta

## Purpose

承载参考实现历史合同档案的迁移能力（扫描文本生成待认领草案、人工认领与批量绑定、未认领时文本兜底）以及在 MySQL 侧回补数据库非空与外键约束的迁移过程，保证存量数据可平滑收敛而不阻塞业务。

## ADDED Requirements

### Requirement: 历史甲乙方文本扫描生成待认领草案

系统 SHALL 提供迁移扫描能力：扫描未绑定往来单位档案且文本非空的合同，按「档案方向 + 原始文本」聚合生成待认领草案，草案 MUST 记录档案方向、原始名称、关联合同数量与状态（待认领/已认领/已忽略）。扫描 MUST 依据合同类型到档案方向的映射决定扫描哪一侧文本，不参与映射的合同类型 MUST 被跳过。扫描 MUST NOT 修改任何合同的甲乙方文本或引用字段。

#### Scenario: 采购合同按乙方聚合
- **WHEN** 库中存在 5 份未绑定供应商档案、乙方文本均为「某某阀门有限公司」的采购合同
- **THEN** 扫描生成 1 条「供应商 + 某某阀门有限公司 + 合同数 5」的待认领草案

#### Scenario: 销售合同按甲方聚合
- **WHEN** 库中存在 3 份未绑定客户档案、甲方文本均为「某某集团」的销售合同
- **THEN** 扫描生成 1 条「客户 + 某某集团 + 合同数 3」的待认领草案

#### Scenario: 不参与映射的类型被跳过
- **WHEN** 一份合同类型为「其他」，其甲乙方文本非空且未绑定档案
- **THEN** 扫描不为其生成任何草案

#### Scenario: 扫描不改动合同
- **WHEN** 用户执行一次扫描
- **THEN** 所有合同的甲乙方文本与档案引用字段与扫描前完全一致

### Requirement: 草案刷新与幂等

重复执行扫描 MUST 幂等：同一「档案方向 + 原始文本」MUST NOT 产生重复草案，已存在草案 MUST 被刷新为最新的关联合同数量。已被认领的草案在后续扫描发现仍有未绑定合同使用同一文本时 MUST 回到待认领状态并清除已匹配的档案引用。已忽略的草案 MUST NOT 被自动改回待认领。

#### Scenario: 重复扫描不重复建草案
- **WHEN** 用户连续执行两次扫描，其间数据无变化
- **THEN** 草案总数不变，第二次扫描仅刷新计数

#### Scenario: 认领后出现新合同则回到待认领
- **WHEN** 一条草案已被认领，随后又有 1 份新合同使用同一文本且未绑定档案，用户再次扫描
- **THEN** 该草案状态回到待认领、已匹配档案被清空，关联合同数量更新

#### Scenario: 已忽略的草案不被自动复活
- **WHEN** 一条草案被标记为已忽略，用户再次扫描
- **THEN** 该草案状态仍为已忽略，MUST NOT 变为待认领

### Requirement: 草案认领与批量绑定

认领能力 MUST 支持两种方式：新建往来单位档案后绑定，或直接绑定到已存在的档案。认领 MUST 按草案的原始名称批量更新所有匹配且未绑定档案的历史合同的档案引用，并 MUST 为每份被更新的合同写入一条含操作人的变更历史。已处于已认领状态的草案 MUST NOT 被重复认领；已忽略的草案 MUST 允许被重新认领。认领新建供应商档案时，若简称缺省 MUST 以草案的原始名称兜底，MUST NOT 因简称缺失而卡住迁移。

#### Scenario: 认领新建档案并批量绑定
- **WHEN** 一条「供应商 + 某某阀门有限公司 + 合同数 4」的待认领草案被认领并新建供应商档案
- **THEN** 4 份历史采购合同的供应商引用被写入该新档案，并且每份合同新增一条含操作人的变更历史

#### Scenario: 认领绑定已有档案
- **WHEN** 用户把一条草案认领到一份已存在的客户档案
- **THEN** 匹配的历史合同客户引用指向该已存在档案，且不新建重复档案

#### Scenario: 已认领草案不可重复认领
- **WHEN** 用户对一条已认领的草案再次提交认领
- **THEN** 系统拒绝并提示该草案已认领

#### Scenario: 已忽略草案可重新认领
- **WHEN** 用户对一条已忽略的草案提交认领
- **THEN** 认领成功，草案状态变为已认领，匹配合同完成绑定

#### Scenario: 供应商简称以原始名称兜底
- **WHEN** 用户认领一条供应商草案并新建档案但未提供简称
- **THEN** 新建供应商档案的简称为草案原始名称，认领成功不被简称校验阻断

### Requirement: 未认领草案不阻塞业务

未认领、已忽略或未生成草案的历史合同 MUST 继续以文本字段正常展示：列表、详情与导出 MUST 正常返回甲方/乙方文本，MUST NOT 因缺少档案引用而报错、隐藏或阻塞。迁移 MUST NOT 强制补齐档案引用。

#### Scenario: 未认领合同正常展示
- **WHEN** 库中存在 10 份未绑定任何档案的历史合同，草案全部处于待认领状态
- **THEN** 合同列表返回 10 条记录并正常展示甲乙方文本

#### Scenario: 未认领合同可正常导出
- **WHEN** 用户导出包含未绑定档案合同的台账
- **THEN** 导出成功，甲方/乙方列输出文本值

### Requirement: 约束回补前必须产出数据体检清单

在把参考实现中「应用层强制、数据库可空」的字段改为非空或补外键之前，系统 MUST 先执行数据体检：对每个待加约束的列统计违例行数 MUST 输出违例清单（列名、违例行数、可定位的主键与违例值），体检 MUST 覆盖待加约束的全部分组。体检未通过时 MUST NOT 执行加约束的 DDL。系统 MUST 在迁移前输出影响行数报告并对受影响表生成快照备份。

#### Scenario: 体检发现违例即阻断
- **WHEN** 体检发现合同的客户引用列存在 7 行非空但指向不存在客户档案的数据
- **THEN** 输出含这 7 行主键的违例清单，并阻断后续加约束的 DDL 执行

#### Scenario: 体检全通过才能继续
- **WHEN** 体检对全部待加约束列均返回 0 违例
- **THEN** 允许进入回填与加约束阶段

#### Scenario: 迁移前输出影响行数报告
- **WHEN** 用户执行迁移准备步骤
- **THEN** 得到一张「表名 / 受影响行数」报告，并已生成受影响表的快照备份

### Requirement: 数据库约束回补范围与口径

系统 MUST 对已确认的字段分组回补数据库级约束：行项引用物料档案的标识、编码与名称，合同引用的客户与供应商档案，合同引用字段，变更历史的操作人、对象类型与对象标识，附件记录的对象类型与对象标识，往来单位与物料的创建人，以及供应商简称。对于业务上确实允许为空的列（单据侧对象的合同引用、附件记录的合同引用、附件对象类型与对象标识、资产类记录里仅用于反查名称的引用列）MUST 保持可空。回补后插入违例数据 MUST 被数据库直接拒绝。

#### Scenario: 行项缺少物料档案被数据库拒绝
- **WHEN** 在约束回补后向行项表插入一行物料档案标识为空的记录
- **THEN** 数据库直接拒绝该插入

#### Scenario: 合同引用不存在的客户档案被拒绝
- **WHEN** 在约束回补后插入一行客户引用指向不存在档案的合同
- **THEN** 数据库直接拒绝该插入

#### Scenario: 供应商简称为空被拒绝
- **WHEN** 在约束回补后插入一行简称为空的供应商档案
- **THEN** 数据库直接拒绝该插入

#### Scenario: 单据侧可空列不被误加约束
- **WHEN** 在约束回补后插入一行未关联任何合同的单据记录
- **THEN** 插入成功（该列按业务口径保持可空）

### Requirement: 迁移与 DDL 编排可一次性在空库执行

本变更集交付的增量 SQL MUST 在空库一次性执行成功，且 MUST 可重复执行（幂等：建表前先删除同名对象、建菜单前先按主键删除再插入）。系统 MUST 提供一份按序执行的初始化编排脚本，新环境按该编排脚本即可得到完整对象集合；上游全量基线文件 MUST 保持原样不修改。

#### Scenario: 空库一次性执行
- **WHEN** 在空库按初始化编排脚本顺序执行全部增量 SQL
- **THEN** 全部语句执行成功，无「对象已存在」或「对象不存在」错误

#### Scenario: 重复执行幂等
- **WHEN** 在同一库上再次执行同一批增量 SQL
- **THEN** 执行成功，菜单与表结构与首次执行后一致

#### Scenario: 基线文件未被修改
- **WHEN** 核对上游全量基线文件
- **THEN** 其内容与变更前一致，本变更集的对象只存在于新增的增量脚本与初始化编排脚本中
