## Goals / Non-Goals

**Goals**

- 把 8 类单据、下推链路、过账/红冲、调拨、盘点、库存明细与流水按参考仓库的**已冻结口径**复刻为可观察行为（见 `specs/erp/**`）。
- 把参考仓库依赖 SQLite 串行写掩盖的两个并发缺陷（无行锁、结存行"先查后插"）在移植时补齐。
- 让模块只提供业务侧新增物（库存域表 + 单据 + 主数据），平台能力（认证/组织/权限/字典/编号/附件/日志/打印）零重复实现。

**Non-Goals**

- 不实现财务凭证、总账、成本核算：库存**只记数量不记成本**；单价仅用于「货品总额度」统计与单据金额展示（`参考仓库-CTMS-移植清单.md` §1.1 口径 D4）。
- 不接入多级审批流：单据保留单级状态机（Q-B7 已确认）；仅**可选**把单据接入 OA 待办入口，不在本变更集范围内。
- 不实现跨组织调拨：调拨限定同一组织内两仓库（参考仓库 Q4 冻结结论）。
- 不实现合同的台账与往来单位档案本身（属 `oa-contract-ledger`），本变更集只消费其能力。
- 不重写前端框架、不替换 element-ui、不引入第二份打印模板或字典。

## Decisions

### D1. 8 类单据：泛型基类 + 每表独立实体，而非"逐表 8 套"或"单表多态"

**选择**：抽单据公共层（表头公共字段 + 行项公共字段 + 状态机动作 + 权限点前缀 + 列表/导出/打印骨架），公共层用泛型基类（`AbstractDocController<T>` / `AbstractDocService<T>`）承载 13 个通用动作；8 类单据各写一个薄子类声明 `doc_type` / `label` / 特有字段 / 权限点前缀。表结构仍是每类表头表 + 行项表独立成表。

**备选与否决理由**：

- 逐表 8 套独立实现：否决 —— 8 倍拷贝，公共规则（状态机、金额口径、下推回写）会各自漂移，参考仓库用工厂 `register_doc_routes` 一套撑 8 类正是为了避免这点。
- 单表多态（一张 `docs` 表 + 类型列）：否决 —— 8 类单据的特有字段差异大（供应商/客户/两仓/盘点类型/生成单号），会退化成大量稀疏可空列；且与参考仓库的字段级清单无法逐条对照，验收困难。
- 参考仓库的"运行期动态拼权限点"：否决 —— 见 D6（显式权限点更可审计）。

**收益**：公共行为只有一份实现，`AC-72`/`AC-73` 的规则对 8 类单据一次生效。

### D2. 过账/红冲：显式事务 + 行锁，事务边界在服务层进入、提交由调用方统一决定

**选择**：审核 = 状态流转 + 过账在同一显式事务内完成（`@Transactional(rollbackFor = Exception.class)`）；过账前对该（物料 × 仓库）的结存行执行 `SELECT ... FOR UPDATE` 加锁后再读取与更新；任一步抛错整体回滚，结存与单据状态都不变。

**备选与否决理由**：

- 沿用参考仓库"服务层不提交 + 路由层一次提交"但**不加锁**：否决 —— 该写法在 SQLite 的串行写下偶然正确，MySQL 下并发审核会丢更新（`参考仓库-CTMS-移植清单.md` §8 #5；PRD F-1）。参考仓库自己的注释也已预告"将来切 PostgreSQL 行锁"。
- 只用乐观锁（版本列 + 重试）：否决 —— 结算场景下重试次数不可控，且行项多时冲突概率高；悲观行锁语义更直白，且不改变对外行为。
- 用数据库唯一索引 + `INSERT ... ON DUPLICATE KEY UPDATE` 完成"加数量"：作为**补充**保留（见 D3），但不足以保证"读到的旧值"正确（负库存校验需要读到准确结存），故仍需行锁。

**对外可观察结果**：见 `specs/erp/stock-ledger/spec.md` 的"并发过账不丢更新"与 `specs/erp/inventory-operations/spec.md` 的"库存不足被拦且不留痕"。

### D3. 结存行并发创建：唯一约束 + 重复键重试

**选择**：结存表在（物料, 仓库）上建唯一约束；过账取结存行时先按唯一键查询并加锁，不存在则插入，捕获重复键冲突后回滚该分支并重试（有限次）；重试后仍冲突则报错。

**备选与否决理由**：

- 只先查后插（参考仓库做法）：否决 —— 两个并发事务可能同时判定"不存在"而双双插入，产生两行结存，直接破坏不变式。
- 全表串行化（锁全表或应用级串行队列）：否决 —— 不可接受的吞吐代价，且掩盖了真正的业务冲突面。
- 用"插入时忽略"再统一重读：可行但会把"插入失败"与"业务校验失败"混淆；采用显式捕获重复键 + 重试更可控。

### D4. 单据审批：保留单级状态机，不接 Flowable

**选择**：单据使用 `draft`/`submitted`/`approved`/`completed`（库存类单据 `approved` 即终态、不使用 `completed`）/`voided` 的状态机，动作守卫是逐动作白名单（提交仅草稿、审核仅待审核、驳回仅待审核、作废仅草稿或待审核、反审核仅已审核或已完成、置完成仅已审核）。可选把"待审核"的单据接入 OA 待办入口以便统一入口。

**备选与否决理由**：

- 接 Flowable 多级审批：否决 —— 业务无多级需求（PRD Q-B7 已确认）；采用后会同时推翻状态机、待办来源与权限判定，并且"审核即过账"的事务边界会被流程引擎的异步节点打散，与 D2 冲突。
- 用 Flowable 但只配单节点：否决 —— 引入引擎事务与业务事务的隔离不确定性，收益为零；Q-B7 的结论是"不接"。

### D5. 库存只记数量不记成本

**选择**：结存表只有数量（按物料计量单位小数位，内部 3 位）；流水上的单价字段是**记录性**字段，仅供「货品总额度」统计与单据展示，不参与结存计算，也不滚动出库成本。

**备选与否决理由**：

- 引入移动加权平均成本层：否决 —— 参考仓库明确不做成本核算（口径 D4/C-05），成本层会要求重算历史、引入会计期间与差异分摊，属另一个变更集；且会改变「货品总额度」的口径定义。
- 完全不记录单价：否决 —— 「货品总额度」与红冲刺减都依赖流水单价，去掉后 `AC-75`/货品总额度无法验收。

### D6. 权限点：显式声明 8 类单据的权限点，不用运行期拼接

**选择**：按 PRD §7.5 命名规范（全小写、冒号分隔、动作集含 `list`/`query`/`add`/`edit`/`remove`/`status`/`submit`/`approve`/`unapprove`/`void`/`push`/`export`/`print`）为 `pur:*` / `sal:*` / `stk:*` 域显式写权限点，并以增量 SQL 写入 `sys_menu`（目录用 `M`、菜单用 `C`、按钮用 `F`，`menu_id` 沿用项目 `9F2C` 前缀并顺延），角色授权由角色管理页勾选。

**备选与否决理由**：

- 参考仓库的"参数化拼接权限点"（`doc_routes` 工厂由参数生成）：否决 —— 在 Java 注解模型下要么用 SpEL 动态表达式（可读性与可审计性差），要么注解丢失；PRD §9.4 第 1 条明确建议显式化。
- 复用 `workflow:*` 权限点：否决 —— 域边界会混乱（库存作业挂在 workflow 域下），且 `AC-80` 要求权限点与菜单一一对应。

### D7. 下推剩余量字段与"归零即完成"

**选择**：行项上保留三个累计字段，按阶段使用 —— 申请→订单用 `ordered_qty`、订单→入库用 `received_qty`、订单→出库用 `shipped_qty`；剩余量 = 原始数量 − 累计字段。**申请→订单阶段在生成草稿下游单据时立即累加**（不等待过账）；**订单→出入库阶段在下游单据过账成功时累加**、红冲时回退且不小于 0。当申请单全部行项剩余量为 0 时自动置 `completed`（幂等）。

**备选与否决理由**：

- 统一下推到"计数落库/过账"再累加：否决 —— 申请单不产生库存动作，没有过账时点；若要求申请单等到订单过账才累加，会导致同一申请行可被重复下推（超量）。
- 用一个 `used_qty` 字段复用三个阶段：否决 —— 会丢失"已下单/已入库/已出库"的区分，`AC-72` 明确要求三字段正确回写；且申请→订单与订单→入库的累加时机不同（前者即时、后者过账），单字段无法表达两种语义。

### D8. 调拨：两阶段先校验后写入，一单两条流水

**选择**：调拨审核分两阶段 —— 阶段一完成全部行的校验（两仓非空且不同、至少一行、每行数量大于 0、调出仓可用量足够），阶段二统一写入（每行：调出仓负数流水 + 调入仓正数流水，同单据号，单价为 0）。任一校验失败直接报错，不产生任何写入。

**备选与否决理由**：

- 逐行边校验边写入：否决 —— 会在"库存不足"这类业务错误上留下"前几行已写"的中间态，需要补偿逻辑；两阶段是参考仓库已验证的写法，且对外行为更清晰（要么全成、要么全不成）。
- 拆成两张单据（调出单 + 调入单）：否决 —— 与参考仓库的"一张调拨单"语义不符，也会让"调拨入库不计入货品总额度"的排除规则失效（调用方需要自己关联两张单）。

### D9. 精度：定点小数 + 先舍入再汇总

**选择**：金额、单价、数量一律定点小数（金额 2 位、单价 4 位、数量按单位小数位、内部 3 位），禁止浮点参与计算或存储；行项金额**先各自四舍五入到 2 位**，单据金额合计等于各行舍入后金额之和；前后端使用同一口径。数量的单位小数位在录入时校验（0 位单位不允许小数数量，超出允许位数被拒）。

**备选与否决理由**：

- 先按高精度求和、最后统一舍入：否决 —— 多行小数单价场景会出现与参考仓库 1 分钱的差异，导致导出/打印/对账三方不一致（C-1、`REQ-NFR-007`、`AC-78`）。
- 用浮点 + 格式化显示：否决 —— 舍入行为不确定，且 `AC-78` 明确要求定点类型。

### D10. 数据范围：显式映射为"创建人 + 归属部门"，不复用系统模块的 AOP

**选择**：单据与结存/流水的可见范围按四档（本人 / 本部门 / 本部门及下级 / 全部）显式实现：创建人归档到"本人"，部门归档到"本部门与下级"，组织树复用平台的部门（`ancestors`）物化路径；多角色叠加取可见范围的**并集**；导出与列表共用同一查询条件（导出即当前筛选、同范围）；**主数据不做数据范围隔离**，档案本身对所有可访问该菜单的人可见。

**备选与否决理由**：

- 直接复用系统的 `@DataScope` AOP：否决 —— 它默认按 `dept_id`/`user_id` 拼 SQL，且当前只覆盖系统模块；参考仓库的"本人"口径基于创建人而非负责人，直接复用会造成"该看的看不到"（风险 R-5）。
- 不做数据范围、全部可见：否决 —— `AC-79`/`BR-V2-08` 要求三层权限真实生效；且与模块边界规格的"数据范围口径显式化"冲突。

**实现注意**：归属部门在单据创建时按创建人的部门**快照**，之后不随人员调岗回溯；这一口径需写进代码注释并覆盖测试。

### D11. 盘点反审核级联与调拨单附件：按文档口径实现（Q-B10）

**选择**：盘点单反审核必须级联处理其生成的盘盈入库单/盘亏出库单（先红冲并作废生成单，再让盘点单回到待审核，且重复处理幂等）；调拨单与其余 7 类单据一样登记附件对象映射（补上参考仓库缺失的 `stock_transfer`）。

**备选与否决理由**：

- 照抄参考仓库现状（盘点反审核无保护、调拨单附件 422）：否决 —— PRD §13.2 的 Q-B10 已确认"按文档口径实现"，且附录 A 第 6、7 条已把两者登记为参考仓库的缺陷；`AC-75` 与本变更集的验收直接对应。

### D12. 前端：配置驱动的单据壳复用，而非 8 份页面拷贝

**选择**：列表页与表单页各自抽一个配置驱动的壳（列定义、筛选、行项表、下推对话框、审核原因弹窗、附件区、打印入口），8 类单据各自只写"壳 + 专有字段插槽"；盘点单因交互特殊（生成行项 → 录入实盘 → 审核）单独实现但复用行项表与状态标签。

**备选与否决理由**：

- 逐页独立实现：否决 —— 参考仓库正是用壳组件撑起 8 个列表页（`DocListPage` 33KB 一个组件），逐页实现会把状态机按钮显隐、范围裁剪、导出语义各写 8 遍。
- 直接移植 Vue3 组合式组件：否决 —— 目标侧是 Vue2 Options API + element-ui 2.15.14；语法层（`v-model` 弹层、日期格式串、消息 API、`link` 按钮）必须改写，后者漏改会**静默出错**。

## Risks / Trade-offs

- [过账/红冲/下推回写的事务一致性：并发审核丢更新会污染库存且难以回溯（R-4）] → 显式事务 + 结存行锁 + 唯一索引与重复键重试（D2/D3）；运维校验/修复接口作为兜底；先做过账并发原型再铺开其余单据；验收用 `AC-74` 的并发实测。
- [金额精度：先汇总再舍入会在多行小数单价场景产生 1 分钱差异，导出/打印/对账不一致（R-6）] → 定点小数 + 先舍入再汇总（D9）；`AC-78` 用"未审核→已审核→打印→导出"四方比对验收；禁止浮点参与计算。
- [数据范围口径差异：复用系统 AOP 会导致越权或"该看的看不到"（R-5）] → 显式映射 + 归属部门快照 + 导出同范围（D10）；用四档账号的可见集合矩阵实测（`AC-79`）。
- [盘亏豁免负库存校验被误当成"通用绕过"而放开面过大] → 豁免只由盘点审核的调亏单过账路径触发，且写在服务方法参数上而非全局参数；规格里给出"盘亏必须过账成功"的具体数值场景。
- [货品总额度口径被改写成"数量变动大于 0"或枚举白名单] → 规格给出红冲刺减与调拨排除的具体数值例子；实现侧以业务类型子串匹配；测试用例直接写这三个数值断言。
- [库存类单据被加上 `completed` 状态导致状态机分叉] → 状态机动作白名单按单据类别裁剪，"置完成"入口对库存类单据不注册；规格用"系统中不存在已完成的库存类单据"表述。
- [盘点反审核级联引入新的失败面（生成单已被人为处理）] → 级联按幂等实现：生成单已作废时跳过，重复调用不报错；规格里显式给出幂等场景。
- [前端全量重写规模与 Element Plus → Element UI 的静默错误（R-7、R-8）] → 用配置驱动壳减少拷贝（D12）；把日期格式串与消息 API 的替换写成检查清单 + grep 门禁；以参考仓库的端到端用例作为行为基线改写。
- [增量 SQL 与 `table.sql` 双轨分叉，新环境初始化缺对象（R-9）] → 新表 DDL 走独立增量脚本并同步补齐基线，按项目已有的初始化编排约定执行。
- [调拨两阶段写入在行数很多时持锁时间变长] → 阶段一先做无锁校验、阶段二才按物料排序加锁写入，缩短持锁窗口；调拨行数在业务上有限（同组织两仓间搬运）。

## Migration Plan

1. **前置**：确认 `oa-v2-overview` 的模块边界与交付门禁已生效；确认 `oa-contract-ledger` 已交付往来单位档案与合同台账（否则单据的"关联合同"与"供应商/客户引用"只能以文本兜底，属降级交付）。
2. **表结构**：新增库存域增量 DDL 脚本（主数据 4 张、单据 8×2 张、结存与流水 2 张），带上唯一索引、外键与非空约束；配套索引按"流水按（物料, 仓库, id）与（单据类型, 单据 id）"建立；同时补齐基线 SQL，使空库可一次性初始化。
3. **字典与参数**：把入库类型、出库类型、盘点范围、计量单位小数位等做成字典类型；把"是否允许负库存"做成系统参数（默认关闭）。
4. **权限与菜单**：增量 `二开-*.sql` 写入 `sys_menu`（采购管理、销售管理、库存管理、资料库下的库存主数据），并给出角色授权指引（角色管理页勾选）；脚本幂等（先删同 id 再插）。
5. **后端**：先落状态机与公共层（S0 冻结后），再按主数据 → 采购线 → 销售线 → 库存过账 → 调拨与盘点 → 库存明细与流水的顺序交付；每个切片带自己的单元/集成测试。
6. **前端**：随各切片交付对应页面（主数据页与单据壳先行），最后做权限点驱动的按钮显隐与菜单联调。
7. **验收**：跑静态审计与越权脚本（`node tools/audit/run-all.js`、`powershell -File .\tools\authz-check.ps1`），再跑端到端链路与并发过账实测；`mvn -B -DskipTests -pl ruoyi-admin clean package` 后核对 jar 时间戳，再用 `"D:\Program Files\Java\jdk-11\bin\java.exe" -jar ruoyi-admin\target\ruoyi-admin.jar` 启动验证。
8. **回滚策略**：
   - 功能级：库存域为独立模块 + 独立菜单，回滚时下架菜单并停用参数即可对既有模块零影响；
   - 数据级：新表为**纯新增**，不修改任何既有表结构，回滚脚本只需按依赖倒序删除新表（行项表 → 单据表 → 结存/流水 → 主数据）与新增菜单行（按 `menu_id` 前缀删除）；
   - 若已产生库存数据，回滚前必须先导出单据、结存与流水留档（`recalc` 校验接口可先确认数据自洽），避免账实信息丢失；
   - 生产回滚**不得**直接改动既有 `sql/table.sql`/`sql/data.sql` 基线内容。

## Open Questions

以下问题不影响本变更集的规格、所选方案与任务拆分，可在实施前或实施中确定：

1. 物料类型未配置编码前缀时，物料编码的自动生成规则取什么（参考仓库退化为固定前缀 + 类型序号；需与业务确认是否接受该退化，或要求类型必须配置编码）。
2. 库存预警（低于安全库存）是否在本批次提供首页看板区块与消息推送；本变更集只要求明细支持"低于安全库存"筛选。
3. 单据的库存明细/流水是否参与本批次的打印与 Excel 导出（参考仓库支持结存与流水导出）；若纳入，导出列配置与"记住上次选择"是否照参考仓库一并提供。
4. 盘点单是否需要在单据上显式记录盘点时点（参考仓库只记录账面快照，靠变更历史与流水时间间接体现）。
5. 单据接入 OA 待办入口的形态（是否统一入口、待办标题与跳转路径约定）；Q-B7 已确认不接 Flowable，此项仅影响入口体验。
6. 数量区间筛选与结存导出的数据量大时的分页/异步导出策略（是本批次按需分页，还是预留异步导出任务）。
