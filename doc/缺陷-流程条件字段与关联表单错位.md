## 4. 根因

### 4.1 直接原因：两条绑定链各指一个表单，且无人纠正

| 绑定链 | 指向 |
| --- | --- |
| 流程 `content.formId` | `DFCD2DC3`（合同会审测试表单） |
| 模板 `t_template.form_id`（模板「测试02-条件分支（排他路由）」`08C77DC1…`） | `DFCD2DC3`（同上） |
| 设计器界面显示并用于提取字段的表单 | `8B1935`（合同类审批单） |

### 4.2 机制原因：**表单"保存"= 软删旧行 + 插新行，而流程/模板里的 `formId` 不会迁移**

- `TemplateDynamicFormMapper.xml`
  - `deleteTemplateDynamicFormById` → `update t_template_dynamic_form set del_flag='1'`（**软删，旧行仍可被按 id 读出**）
  - `selectFormOptionList`（**下拉候选**）→ `where enable_flag='1' and del_flag='0'`（**只列有效行**）
  - `selectTemplateDynamicFormById`（**按 id 取表单**）→ **不校验 `del_flag` / `enable_flag`**

⇒ 表单每保存一次就多出一行"同内容不同 id"的新行，旧行变成 `del_flag=1`；而流程内容与模板里的 `form_id` **是两把独立的钥匙**，可以静默分叉，系统里**没有任何一致性检查**。

### 4.3 放大原因：设计器仍可手打字段名绕过 V-8

`src/views/workflow/simple-flow/ConditionEditor.vue` 的字段下拉带 **`allow-create`**（第 30 行）：

> 已关联表单时，字段本应从表单提取并**只能选必填字段**（未设必填的置灰），但 `allow-create` 允许**直接手敲任意字段名**，可绕过整个 V-8 检查。

### 4.4 未实现：PRD V-8 要求的"表单保存时反向校验"

`doc/PRD-合同审批二开.md` 第 564 行原文要求：

> 条件字段必须是表单中存在的、且为"必填"的字段；**表单设计保存时反向校验**（字段被删/改为非必填 → 阻断并列出受影响的流程）

**代码中未实现**（后端/前端全库检索"受影响的流程 / 反向校验"均无命中）⇒ 表单改字段名之后，受影响的流程不会得到任何提示。

### 4.5 精确机制：表单换版本时**模板会改指、流程不会**（决定性）

`TemplateDynamicFormServiceImpl#updateTemplateDynamicForm`（动态表单**版本化**）一个事务里做三件事：

| # | 动作 | 代码 |
| --- | --- | --- |
| ① | 旧版本行**停用**（`enable_flag='0'`） | `templateDynamicForm.setEnableFlag(NO)` |
| ② | **插入一个新版本行**（新 UUID，内容为改后的） | `newDynamicForm.setId(IdUtils.fastSimpleUUID())` |
| ③ | **把模板改指到新版本** | `templateMapper.repointFormId(old, new)` |

而第 ③ 步的 SQL **只动 `t_template`**：

```xml
<!-- TemplateMapper.xml:237 -->
<update id="repointFormId">
    update t_template set form_id = #{newFormId}, update_time = now()
     where form_id = #{oldFormId}
</update>
```

**`t_flow_simple.content` 里的 `formId` 不在改指范围内** ⇒
表单每保存一次，模板跟着走、**流程留在旧版本**，而设计器的字段清单按流程内容里的 `formId` 取
（`FlowDesigner#loadFlow` / `loadEmbeddedForm`）—— 这正是"界面显示 A、校验按 B"的成因。

> 实测复现（本轮改表单字段名时亲眼看到）：
> 1. 表单 `8B1935`（`enable_flag=1`）改 label 走 `PUT /template/dynamic/form`
> 2. 生成新版本 `5504ED72`（`enable_flag=1`），旧版 `8B1935` 变 `enable_flag=0`
> 3. 模板 `08C77DC1` 的 `form_id` **自动**从 `8B1935` 变成 `5504ED72` ✅
> 4. 同一时刻流程 `testCondition.content.formId` **仍是 `8B1935`** ❌ —— 必须人工同步

### 6.4.1 补齐轮次（同日再追加）：枚举字段的值控件改为**选择器**

**问题（用户反馈）**：条件选了单选类字段后，右边的"值"仍是**自由输入框**（截图：`合同类型（field101…` + `等于` + 输入框 `经营`）。

**改法**：值控件按字段类型分流 ——

| 字段控件 | 值控件 | 候选 |
| --- | --- | --- |
| `el-radio-group` / `el-select`（单选型枚举） | **`el-select` 选择器** | 该字段的选项 **label**（如 经营/经济/人力/行政），可搜索 |
| `el-checkbox-group`（多选） | **仍是输入框** | 条件对多选无法表达"等于某一个"，且 V-8 只认必填字段 |
| 其它（输入/金额/时长…） | 仍是输入框 | 无候选项 |
| 未关联表单 / 选项表缺失 | 仍是输入框 | **绝不把值控件变没**（否则条件无法填写） |
| 比较符 = 为空 / 不为空 | 选择器/输入框**置灰** | 无需值 |

判据收口为纯函数 `pickerOptions / useValuePicker / needsValue`（`conditionText.js`），并补 9 条用例。

**⚠ 选择器写进条件的是选项 `label`，不是 `value`** —— 这条口径**实证来源**（此前我一度推断为 value，是错的）：

```java
// BizFormServiceImpl#convertValueToLabel（行 296-360 分发 / 446-455 单选）
case EL_RADIO_GROUP: handleRadioLabel(valData, field, vModel, value); break;
...
private void handleRadioLabel(...) {
    for (Object opt : options) {
        if (option.get(VALUE_FIELD).equals(value)) {
            valData.put(vModel, option.getString(LABEL_FIELD));   // ← 1 → "经营"
            break;
        }
    }
}
// 行 524-553：转换后的 valData 才写进流程变量
runtimeService.setVariables(procInstId, valData);
```

⇒ 前端提交的是**原始 value**（`field101 = 1`，`render.js:57` 的 `:label="item.value"`），
后端**翻译成 label** 之后才进流程变量。所以条件里必须写 `经营`；写成 `1` 运行期**恒不成立**。
（`t_workflow_form.form_data` 里另存了原始 `valData`，那是展示/留痕口径，不是流程变量口径。）

**实测**：抽屉里值控件变为下拉、展开后候选正是 `经营 / 经济 / 人力 / 行政`（表单真实选项）；选择后画布仍为 `当 合同类型 = 经营 时`；保存后落库仍为 `field101 EQ '经营'`。

## 11. 第五轮（同日）：**发布校验报的问题与眼前画布对不上**（已修，纯前端）

> 与 §10 同属简化流程设计器，但**成因完全不同**：§10 是"写入口径不随多人方式收敛"，
> 本条是"**校验读的是库里的旧内容**"。用户原话：
> ①「阻断项提示需要直接提示那个审批阶段存在问题」；②「提示项我已经加了多个审批节点、检查为什么还会有提示」。

### 11.1 现象

画布上明显有 **4 个审批节点**（顶层 2 个 + 条件分支内 2 个），点「发布」却弹：

```
发布校验未通过
阻断项（必须修复）
· [V-2] 节点 n_first：节点「审批节点」选择「指定人员」但未选人
提示项
· [V-1] 只有 1 个审批节点：不会产生待办，建议至少 2 个
```

两个都"说不通"：`n_first` 在画布上叫「发起部门审核」、并且**已经选了超级管理员**；审批节点也远不止 1 个。

### 11.2 根因（一条，同时解释两个"说不通"）

`handlePublish()` 直接调 `POST /workflow/simple-flow/validate {id}`，
而**后端是按 `id` 读 `t_flow_simple.content` 校验的** —— 它**看不到画布上还没保存的改动**。
于是"发布"校验的是**上一次保存的内容**：

| 报的问题 | 真实解释 |
| --- | --- |
| `[V-2] 节点 n_first` | `n_first` 是**旧内容**里的节点（那时它没选人、也还叫「审批节点」）。用户随后在画布上改了名、选了人 —— **改动只在内存里**，库里的旧行没变 |
| `[V-1] 只有 1 个审批节点` | 同一个原因：旧内容的 `approveCount` 就是 1，用户后来加的 3 个节点还没落盘 |

**实测反证**：直接把库里的 content 拿出来数 —— `approve 计数 = 4`（顶层 2 + 分支内 2），
而弹窗说 1 ⇒ **两边看的是两份不同的内容**，不是"计数器算错了"。
（顺手核过 `SimpleFlowValidator`：V-1 的 `approveCount` 是 `+=` 累加的，顶层与分支内都会数；
V-2 的文案本身就带节点名 —— 校验器没问题，是**喂给它的内容过期**。）

### 11.3 修复（纯前端，1 个文件）

| 位置 | 改动 |
| --- | --- |
| `FlowDesigner.vue` · `handlePublish` | **先存当前画布，再校验**：抽出 `saveDraftQuietly()`，`handlePublish` = `saveDraftQuietly()` → `validateThenPublish()`；保存失败就报"发布前保存草稿失败"并中止（不拿旧内容去校验） |
| `FlowDesigner.vue` · `showIssues` | 阻断项后面补一句**画布定位**：`（画布上叫「XXX」）`；按 id 在当前流程树里递归反查（含分支内节点）。**查不到时显式说明**"当前画布上找不到这个节点，请重新保存后再校验"——那种情况正是内容不同步的信号 |
| `FlowDesigner.vue` · 新增 `nodeNameById()` | 上面的反查（顶层 + 分支递归） |

> 顺带解决了一个隐性风险：原来"改了画布但没保存就点发布"，**发布出去的也是旧内容** ——
> 用户以为"我改完发布了"，其实引擎部署的是上一次的版本。现在保存-校验-发布用的是同一份内容。
