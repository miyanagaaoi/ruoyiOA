# 缺陷报告 · 并行会审「全部完成」不合流

> **发现日期**：2026-10-04　**发现方式**：真实业务模拟（API 发起 → 多账号审批）
> **严重级别**：**高** —— 单据会永久卡死，无法办结
> **状态**：已定位根因，**未修复**

---

## 1. 现象

走 `testParallel`（`joinMode=ALL`，4 个会审部门）：

1. 发起 → 「责任部门审批」—— 正常
2. 提交该节点 → **同时生成 4 个「会审部门」任务**，各分配给 4 个不同用户 —— 正常
3. 4 个用户**各自审批完毕** —— 任务全部消失
4. **❌ 流程没有结束**：活动任务 0 个，但实例仍是「进行中」（`ACT_HI_PROCINST.END_TIME_` 为 NULL）

数据库证据：

```
ACT_RU_TASK           WHERE PROC_INST_ID_='1090024'   → 0 行（任务确实都办完了）
ACT_HI_TASKINST       → 4 条 p1，四条 END_TIME_ 都有值（确实都完成了）
ACT_HI_ACTINST        → start / Flow_1 / n1 / Flow_2 / p1×4，**没有 Flow_3、没有 end**
ACT_HI_PROCINST       → END_TIME_ = NULL  ← 卡住
```

对比：**`joinMode=ANY`（`${nrOfCompletedInstances >= 1}`）完全正常** ——
`testParallelAny` 生成 3 个任务，只完成 1 个，流程**立即结束**（`END_TIME=14:29:25.855`），剩余任务 0。

再对比：**条件分支流程完全正常** ——
`testCondition` 走完全程：`start → n1 → c1(排他网关) → n2 → end`，`END_TIME=14:29:00.727` ✓

### 结论：不是"结束节点坏了"，也不是"多实例机制坏了"，而是**专属于 ALL 合流条件**

| 场景 | 结果 |
| --- | --- |
| 串行 → 结束 | ✅ 未单独测 |
| 条件分支 → 结束 | ✅ 正常结束 |
| 并行（ANY：任一完成即合流） | ✅ 正常结束 |
| **并行（ALL：全部完成才合流）** | ❌ **卡住，永不结束** |

---

## 2. 根因（有数据库硬证据）

编译器为 `joinMode=ALL` 生成的完成条件是：

```xml
<multiInstanceLoopCharacteristics isSequential="false"
    flowable:collection="jointDepts" flowable:elementVariable="dept">
  <completionCondition xsi:type="tFormalExpression">
    <![CDATA[${nrOfCompletedInstances == nrOfInstances}]]>
  </completionCondition>
</multiInstanceLoopCharacteristics>
```

运行时这两个计数变量的实际存储：

```
TYPE_ = integer                              NAME_ = nrOfInstances            LONG_ = 4       ✓ 正常
TYPE_ = bpmnParallelMultiInstanceCompleted   NAME_ = nrOfCompletedInstances   LONG_ = NULL    ✗ 不是数字
TYPE_ = bpmnParallelMultiInstanceCompleted   NAME_ = nrOfActiveInstances      LONG_ = NULL    ✗ 不是数字
```

**`nrOfCompletedInstances` 是一个 `bpmnParallelMultiInstanceCompleted` 类型的标记对象，数值为 NULL。**

因此 `${nrOfCompletedInstances == nrOfInstances}` 是「拿一个对象去和整数 4 比较」，
**永远为 false** → 多实例永远不会通过完成条件收敛。

> ⚠️ 为什么 `ANY` 的 `${nrOfCompletedInstances >= 1}` 反而能工作，尚未查明。
> 一种可能是两条路径不同（早合流 vs 自然结束），另一种可能是这与下面 §3 的第二个可疑点有关。**需要进一步定位**。

## 3. 第二个可疑点（待排查）

本项目的 Flowable schema 与标准版有差异，且 RuoYi-OA **自带多实例操作接口**：

```
/workflow/handle/deleteMultiTask/list
/workflow/handle/deleteMultiInstanceExecution
/workflow/handle/addMultiInstanceExecution
```

而 `FlowHandleServiceImpl.completeTask()` 在完成任务后还会执行：

```java
flowTaskService.complete(flowTaskVo);
List<Todo> nextTodos = todoService.createNextTodo(flowTaskVo, createId, false);
handleNextTodos(nextTodos, flowTaskVo);
handleOtherOperation(nextTodos, createId, true);   // ← 这里可能改动了 MI 执行
```

`ACT_RU_EXECUTION` 里该实例的状态很反常：

```
ID_        PARENT_ID_  ACT_ID_  IS_ACTIVE_  IS_SCOPE_   ← 多实例根通常是 scope=1，这里是 0
1090024    NULL        NULL     1           1           ← 流程实例根，在等活动
1090041    1090024     p1       0           0           ← 多实例根
1090045-48 1090041     p1       0           0           ← 4 个分支
```

**多实例根 `IS_ACTIVE_=0` 且没有向 `end` 推进** —— 高度怀疑 `handleOtherOperation` 之类的补偿逻辑在最后一个分支完成时，
把 MI 执行置成了一种"已完成但未推进"的状态。

另外该 schema **没有 `ACT_RU_INCIDENT` 表**，`ACT_RU_JOB` 的列名也与标准版不同，
所以无法从 incident 表确认表达式是否抛过异常。

## 4. 修复方向（建议按序验证）

### 方向 A（最小改动，优先验证）

**ALL 合流时不要生成 `completionCondition`。**

并行多实例的 BPMN 语义是：**所有实例自然完成后，多实例活动自动完成** ——
根本不需要用完成条件来表达"全部完成"。加上这个条件反而是多余的，
而在本环境里它成了一个永远为 false 的表达式。

改动位置：`SimpleFlowCompiler` 的并行分支段（`e.miCompletion`），
`joinMode=ALL` 时置空，仅 `ANY` 时生成 `${nrOfCompletedInstances >= 1}`。

```java
e.miCompletion = SimpleFlowDef.JOIN_ANY.equals(node.getJoinMode())
        ? "${nrOfCompletedInstances >= 1}"
        : null;   // ALL：交给引擎的默认语义（全部完成即完成），不要条件
```

### 方向 B（若 A 无效）

排查 `FlowHandleServiceImpl.completeTask` → `handleOtherOperation` 是否在最后一个分支完成时
破坏了多实例执行的推进。可用「不经过 RuoYi 封装、直接调 Flowable `taskService.complete`」
做对照实验来隔离。

### 方向 C（保底）

把 ALL 也编译成 `${nrOfCompletedInstances >= 1}` 之外的形式不可行；
若 A/B 都不通，退而求其次：**ALL 场景改用「并行网关 + N 条用户任务」而不是多实例**，
用网关的 join 语义保证合流。

## 6. 为什么开发期的冒烟测试没发现

开发阶段在一次性库 `flow_smoke` 上验证多实例时，断言写的是
**"全部完成后没有剩余任务"** —— 而卡住的实例恰好也满足这一条（任务确实都办完了）。

**漏掉的断言是：流程实例本身必须结束（`ACT_HI_PROCINST.END_TIME_` 非空、历史里出现 `end` 事件）。**

这条教训值得记：**多实例流程的验收标准不能只看"任务清空"，必须看"实例办结"。**

## 7. 影响面

| 功能 | 是否受影响 |
| --- | --- |
| 串行审批 | 不受影响（无多实例） |
| 会签（AND，单人节点多人） | **需复测**（也是多实例，且用的正是 `${nrOfCompletedInstances == nrOfInstances}`） |
| 或签（OR） | 需复测（`>= 1`） |
| 并行会审 `joinMode=ANY` | ✅ 已验证正常 |
| **并行会审 `joinMode=ALL`** | ❌ **卡死** |
| 条件分支 | 不受影响（已端到端验证正常） |

> ⚠️ **会签很可能同样中招** —— 编译器给 AND 用的完成条件与 ALL 完全相同，
> 只是集合来源是"节点参与人"而不是"表单多选字段"。
