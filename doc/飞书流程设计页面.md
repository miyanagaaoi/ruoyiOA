# 第一部分 · 设计层面

## 1. 页面骨架：四区布局

```
┌ 顶部栏 ─────────────────────────────────────────────────────────────────┐
│ 事项审批    草稿（保存于 4 分钟前）▾      预览 · 发布 · 创建限时审批 · 创建自动化 │
├ 四步向导 ───────────────────────────────────────────────────────────────┤
│ ① 基础信息   ② 表单设计   ③ 流程设计   ④ 更多设置                          │
├────────────────────────────────────┬────────────────────────────────────┤
│  画布（自动布局树，非自由画布）        │  上下文配置面板（随选中整体替换）      │
│                                    │                                    │
│   提交                             │  选中「提交」 → 谁可以提交 + 表单权限   │
│    +                               │  选中「审批」 → 审批人 + 去重 + 表单权限 │
│   审批（直属部门负责人）              │  选中「条件」 → 优先级 + 条件组        │
│    + 添加条件分支                   │  选中「抄送」 → 10 种来源 + 表单权限    │
│   ├ 条件分支 1   优先级 1            │  选中「办理」 → 说明 + 与审批人的区别    │
│   │   └ 审批 → [添加并行分支]         │                                    │
│   └ 其他情况    优先级 2             │  每个面板统一四段式：                  │
│        └ 审批 → 抄送                │  ①设置项 ②表单权限 ③提示 ④取消/保存     │
│   结束                             │                                    │
│                          缩放 100%  │                                    │
└────────────────────────────────────┴────────────────────────────────────┘
```

**四区职责**（实测）

| 区 | 内容 | 职责 |
| --- | --- | --- |
| 顶部栏 | 审批名 + 草稿状态 + 全局动作 | 状态可见性 + 全局出口（预览/发布） |
| 四步向导 | 基础信息 / 表单设计 / 流程设计 / 更多设置 | 把"定义一个审批"切成四个心理阶段 |
| 画布 | 纵向主链 + 并列分支泳道 + `+` 连接点 | **只表达结构**：顺序、分叉、合流 |
| 右面板 | 选中元素的全部配置 | **只表达属性**：参数、权限、提示 |

## 2. 四个核心设计决策

| # | 决策 | 具体做法 | 解决什么 |
| --- | --- | --- | --- |
| D1 | **结构 / 属性分离** | 画布不放任何输入框；所有参数进右面板 | 画布永不被字段挤爆；结构一眼看清 |
| D2 | **选中即上下文** | 右面板不是固定长表单，而是**整体替换** | 一屏内配完，不跳页、不迷路 |
| D3 | **插入入口唯一化** | 所有 `+` 固定在同一条纵轴上 | 插入点不用找，形成"隐式表格"的阅读节奏 |
| D4 | **容器 = 卡片泳道** | 分叉不是菱形网关，而是并排卡片列 | 业务用户不需要懂"排他网关/并行网关" |

> D4 是这套设计最关键的一点：**把 BPMN 的网关概念在 UI 层彻底消灭**。管理员看到的是"条件分支 1 / 其他情况"，不是"排他网关 / 默认流"。

## 3. 配置面板的「四段式」骨架

四类面板内容完全不同，但骨架**完全一致**（实测）：

```
① 设置项         ← 该节点独有配置
② 表单权限       ← 每个节点都有（本节点能看到 / 编辑哪些字段）
③ 提示           ← 常驻内联提示
④ 取消 · 保存     ← 面板级事务
```

**价值**：管理员学一次，四处适用。这是"配置密度极高却不觉得乱"的根本原因。

**注意 ④ 的语义**：面板是**事务性**的——改完点保存才生效，点取消回滚。这是与"即时生效"截然不同的选择，直接决定前端状态管理方案（见 §12）。

## 4. 提示系统的三层

| 层 | 形式 | 实测例子 | 作用 |
| --- | --- | --- | --- |
| 内联提示 | 常驻文字 | "抄送的人数最多支持 100 人以内" | 边界前置，不用试错 |
| tooltip | 悬停 | 13 种审批人来源各配一条解释 | 术语自解释，不占版面 |
| 帮助链接 | 外跳 | "如何设置条件 ?" → 帮助中心；"与审批人的区别？" | 长文档推出去，页面保持干净 |

措辞是**预防式**的（实测原文）：

> "为避免部分员工未设置上级导致流程错误，可前往**飞书管理后台**检查"

**在用户即将踩坑前给出路**，而不是等提交失败才报错。

## 5. 视觉编码（推断，基于画布截图）

| 元素 | 编码 | 含义 |
| --- | --- | --- |
| 提交 / 结束 | 灰蓝色圆角卡 | 流程端点 |
| **审批** | **橙色 + 顶部色条** | 决策节点（最需要被看见的） |
| 抄送 | 浅色 / 虚线 | 知会，无决策权 |
| 办理 | 另一种样式 | 业务动作（打款、盖章） |
| 条件分支 1 | 蓝色标签 | 路由容器 |
| **优先级 1** | **绿色 badge** | 显式优先次序 |
| 其他情况 ⓘ | 灰字 | 系统生成，不可编辑 |
| 选中态 | 边框加粗 + 高亮 | 与右侧面板联动 |

一句话：**橙色只给"要人做决定"的节点**，其余全部降噪。这是全页最强的视觉纪律。

## 6. 渐进披露

- **四步向导**：每步只面对一类问题，不要求管理员一次想清楚所有事
- **高级能力外置**：`创建限时审批`、`创建自动化` 放右上角，不占主画布注意力
- **复杂配置入弹窗/抽屉**：条件组、办理人解释、抄送人选择都是独立弹层

## 7. 实测到的缺陷（不建议照抄）

| # | 缺陷 | 证据 | 后果 |
| --- | --- | --- | --- |
| F1 | **横向无限膨胀** | 事项审批已有 2 条件分支 × 各含并行容器 + 抄送；只有右下角 `100%` 缩放 | 没有折叠 / 缩略导航 / 面包屑，分支一多就要靠缩放硬看（`state-coverage` 的 edge 态没兜住） |
| F2 | **并行分支也带「其他情况」** | 两处并行容器下都有"其他情况" | 并行=多支同时流转，再加"没命中走这里"的兜底语义自相矛盾 |
| F3 | **重复建模** | 两条条件分支里各放了一份**完全相同**的"并行分支 1 当 费用汇总 > 0 → 审批（财务）" | 同一业务规则维护两遍，规则变更必漏改一处 |
| F4 | **连接点 `+` 命中区偏小** | 截图中 `+` 为小圆形，居中悬浮 | Fitts's Law：全画布唯一插入入口，却最难点 |
| F5 | **术语密度高** | 审批人来源 13 项含"节点审批人 / 连续多级上级 / 指定审批层级" | Hick's Law 选择过载；靠 tooltip 缓解，但仍需管理员理解三者差别 |

## 8. 可迁移的设计原则（6 条）

1. **结构与属性分离** —— 画布管结构，面板管参数
2. **选中即上下文** —— 右面板整体替换，不做长页面锚点跳转
3. **插入点唯一化** —— 同一条轴上的 `+`
4. **容器用卡片泳道表达** —— UI 层不暴露网关概念
5. **面板骨架统一** —— 学一次用四处
6. **提示分三层** —— 内联讲边界、tooltip 讲术语、外链讲文档

# 第二部分 · 代码层面

## 9. 数据模型：容器嵌套树

飞书这套界面在数据上只有一种模型——**带容器的节点树**：

```ts
type Node =
  | { id: string; type: 'start'; name: string; submitScope: Scope[] }
  | { id: string; type: 'approve'; name: string; assignee: Assignee; dedupe: boolean; formAuth: FormAuth }
  | { id: string; type: 'handle';  name: string; handler: Assignee; formAuth: FormAuth; actionAuth: ActionAuth }
  | { id: string; type: 'cc';      name: string; ccers: Ccer[]; formAuth: FormAuth }
  | { id: string; type: 'condition'; name: string; lanes: Lane[] }   // 排他路由
  | { id: string; type: 'parallel';  name: string; lanes: Lane[] }   // 多支并行
  | { id: string; type: 'end'; name: string; ccers: Ccer[] }

type Lane = {
  id: string
  name: string                    // "条件分支 1" / "其他情况"
  priority?: number               // 实测：优先级 1 / 优先级 2（仅排他容器）
  fallback?: boolean              // true = 「其他情况」，系统生成，不可编辑不可删
  condition?: ConditionGroup[]    // 组内「且」、组间「或」
  nodes: Node[]                   // ← 泳道内是一条完整的子链
}
```

**三个关键点**：

1. **容器与节点同构**（都是 `Node`）→ 递归渲染天然支持任意层嵌套（实测：条件分支 → 泳道 → 并行容器 → 泳道 → 审批）。
2. **泳道内是"链"而不是"单节点"** → 这是为什么飞书能把"审批 → 并行容器 → 审批 → 抄送"整段放进一条分支。
3. **兜底是泳道的属性**，不是独立节点 → `fallback: true` 的泳道编译为流程引擎的默认流。

> **与本项目现状的对照**：我们的 `SimpleFlowDef` 已经是这个形状
> （`condition.branches[]` 就等价于 `lanes`，`branch.defaultBranch` 等价于 `fallback`），
> **数据模型不需要改**；缺的是"显式优先级"字段和"泳道内可放容器"（我们目前 V-11 禁止嵌套）。

## 10. 布局算法：CSS Flex 承担 90%，只有分叉横杠要算

**不要手算坐标**（不要引入 dagre / elkjs）。这套结构是"纵向主链 + 横向并列"的正交布局，CSS Flex 天然能做：

```css
/* 链：纵向 */
.chain   { display: flex; flex-direction: column; align-items: center; }
/* 容器：泳道并排 */
.lanes   { display: flex; flex-direction: row;    align-items: flex-start; }
/* 泳道：内部还是纵向链 */
.lane    { display: flex; flex-direction: column; align-items: center; flex: 1; }
```

**唯一需要计算的**是分叉 / 汇合的横杠位置。n 条泳道时，横杠应从**第 1 条泳道中心**连到**第 n 条泳道中心**：

```js
// 每条泳道占 100/n 宽度，中心分别在 50/n % 和 100 - 50/n %
const leftPct  = 50 / n
const rightPct = 50 / n
```

```css
.split-bar {
  position: absolute;
  left:  calc(50% / var(--lanes));
  right: calc(50% / var(--lanes));
  height: 1px; background: #d0d0d0;
}
```

**验证**：`n = 2` → `left/right = 25%` —— 正是 `wireframes.html` 里写死的值。
`n = 3` → `16.67%`。

> ⚠️ **这正是我在 `wireframes.html` 里发现的 bug**：原型的 `.split-bar{left:25%;right:25%}` 与 `stubs` 里**写死 2 个 span**，一旦加到 3 条分支，分叉线就与泳道错位。
> **正确做法**：把泳道数通过 CSS 变量注入（`--lanes`），或用 `style="--lanes: 3"` 内联下发。
> **单泳道退化**：`n = 1` 时不该画分叉（`left == right == 50%`，视觉上退化为一条直线，需显式隐藏横杠）。

## 11. 渲染架构：递归组件树

```
<FlowChain :nodes="nodes">            ← 纵向链（递归入口）
   ├─ <FlowNode v-for>                ← 单节点卡片（按 type 决定配色与摘要）
   ├─ <FlowConnector @insert>         ← 「＋」连接点（唯一插入入口）
   └─ <FlowContainer v-if="isContainer(node)">
        ├─ <FlowSplitBar :lanes="n" /> ← 分叉横杠（§10）
        ├─ <FlowLane v-for="lane in node.lanes">
        │     ├─ <LaneHeader>          ← 名称 + 优先级 badge + 条件 chip + ⓘ
        │     └─ <FlowChain :nodes="lane.nodes" />   ← ★ 递归
        └─ <FlowMergeBar :lanes="n" /> ← 汇合横杠
```

**Vue2 递归的四个坑**：

| 坑 | 说明 | 对策 |
| --- | --- | --- |
| 组件自引用 | 需要 `name` 选项 | `name: 'FlowChain'`，模板里直接写 `<FlowChain>` |
| **`v-for` 的 key** | 用 `index` → 结构编辑时复用错组件实例、丢焦点、动画错乱 | **必须用节点 `id`**（新节点创建时即生成 uuid） |
| 深层 `$emit` 穿透 | 递归层里点 `+` / 删除，事件要冒到顶层 | 注入（`provide/inject`）一个 `dispatch(action, path)`，不要层层 `$emit` |
| 性能 | 每次输入都触发整棵树 re-render | 面板编辑**独立于画布**：编辑态放面板局部 data，保存时才提交进树（呼应 §3 的事务语义） |

## 12. 交互与状态管理

### 12.1 选中态必须用「路径寻址」

扁平下标**不够用**——分支内的节点在数据上不在顶层数组里。我们已经在真实代码里踩过这个坑：最初 `activeIndex: number` 只能指顶层，导致**分支内的审批节点根本点不进去配置**，最终必然被发布校验以「未配置参与人」拦下。

```js
// ❌ 只能指顶层
selection = 2
// ✅ 路径寻址
selection = { kind: 'branch', index: 2, branchId: 'b_xxx', subIndex: 0 }
// ✅✅ 若放开任意深嵌套，改成纯路径
selection = { path: [2, 'lane_b1', 1] }   // 层层下钻的 key 序列
```

**推论**：容器嵌套一旦超过 2 层，`{kind,index,branchId,subIndex}` 就会失效，必须换成 `path: (number|string)[]`。**如果确定要做飞书那种嵌套，第一天就把 `path` 定下来，别用中间态。**

### 12.2 编辑事务：二选一，不要混

| 方案 | 语义 | 适用 | 代价 |
| --- | --- | --- | --- |
| **面板级事务**（飞书） | 面板内改草值 → 保存才提交进树；取消回滚 | 配置项多的面板（审批人、条件组） | 每个面板要维护 `draft` + `original` |
| **即时编辑** | 改一下立即写进树，顶部统一"保存流程" | 简单开关、名称 | 误操作无回滚，需撤销栈 |

**现状**：我们用的是"即时编辑 + 顶部保存草稿"。这对"名称/开关"够用，但对**条件组**（多行多组、结构复杂）不合适——必须改回面板级事务。

### 12.3 撤销 / 重做

结构树体积小（几十个节点），**整树不可变快照 + 栈**就够了，不必上命令模式：

```js
history = [snapshot0, snapshot1, ...]   // 每次"结构性操作"（插入/删除/移动/改条件）压一帧
// 深拷贝成本可忽略（< 50KB JSON）
```

## 13. 与后端契约

```
设计器（前端）                      后端                          流程引擎
─────────────                    ─────────                     ──────────
容器嵌套树 JSON  ──保存──▶  t_flow_simple.content
                                 │
                       校验 V-1..V-12
                                 │
                       SimpleFlowCompiler
                       （树 → BPMN XML，含排他网关/多实例）
                                 │
                        saveFile(name, category, xml) ──部署──▶ ACT_RE_PROCDEF
```

**三条硬约定**（我们已实现并有真实引擎验证）：

1. **前端绝不生成引擎产物**。前端只产出树 JSON；BPMN 由后端编译。否则前端会慢慢长出第二套流程语义。
2. **条件分支必须编译为排他网关**，条件写在网关的出口顺序流上，兜底走 `default` 流。**禁止把条件直接挂在用户任务的多条出口上**——BPMN 原生语义下多条为真会**并行执行**，条件分支会静默退化成并行分支（本项目 `conditionPanel.vue:11-13` 的官方提示原文即为此）。
3. **并行分支编译为多实例用户任务**（集合 = 表单多选字段），**不用并行网关**。已实测：集合为空自动跳过、全部完成自动合流、或签 `${nrOfCompletedInstances >= 1}` 生效。

| R6 | 编辑事务混乱 | 复杂面板走**面板级事务**（draft → 保存提交） |
| R7 | 并行分支被加上兜底 | **不设**；并行容器不渲染 lane fallback（补飞书 F2） |
| R8 | 重复建模无提示 | 发布校验里加"两条泳道存在同构子链"的相似度提示（补飞书 F3） |
| R9 | 连接点太小 | 命中区 ≥ 24×24px（补飞书 F4） |
| R10 | 异常被静默吞掉 | 所有接口 `.catch` 必须给错误态呈现（`state-coverage` 五态要求） |

## 16. 工作量估算（含嵌套）

| 范围 | 内容 | 轮次 | 墙钟 | Token（输入/输出） |
| --- | --- | --- | --- | --- |
| **第一步**：并列树（一层嵌套，不动数据模型与编译器） | 递归渲染 + 连接点 + 横杠算法 + SCSS | 8–12 | 2–3 h | 0.8–1.2M / 60–90k |
| **第二步**：放开嵌套（条件泳道内可放并行容器） | 编译器递归 emit + V-11 改限深 + 冒烟单测 | 6–10 | 1.5–2.5 h | 0.6–1M / 40–70k |
| **第三步**（可选）：拖拽 | 同链排序（vuedraggable 已在依赖里）/ 跨容器拖 | 2–3 / 5–8 | 0.5–2 h | 0.2–0.6M / 15–40k |

> 第一步的主要工作量在 **SCSS 的分叉汇合对齐**，第二步的主要风险在**编译器的嵌套正确性**（已有真实引擎冒烟测试兜底）。
