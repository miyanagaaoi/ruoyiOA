# 缺陷：「多人方式 = 单人」时，指定人员仍能勾选多人（2026-10-05 第四轮，已修）

> 面向对象：接手「简化流程设计器」的 Agent / 复核者。
> 一句话：**审批节点的「多人方式」选了「单人」，「选择人员」弹窗却允许勾任意多个人**；
> 这不只是界面瑕疵 —— 编译期按"指定人员的人数"决定生成 `assignee` 还是 `candidateUsers`，
> 于是**配置是单人、跑起来是候选人抢单**。
> 状态：**纯前端已修**（`assigneeMapping.js` + `FlowDesigner.vue`），**后端与数据零改动**。
> 关联记录：`doc\缺陷-流程条件字段与关联表单错位.md`（同一轮接手、同一设计器的另一处缺陷）。

---

## 1. 现象

1. 打开流程设计页（例：`/workflow/simple-flow/designer?id=f2578b68795447aa8412bb8ebd4d06b2`，流程 `testCondition`）；
2. 点任一审批节点 → 「参与人来源」= **指定人员**；
3. 「多人方式」保持默认的 **单人**；
4. 点「选择人员」→ 共享选人弹窗（`components/org/UserAllSelect`）里**能勾选任意多个人**；
5. 确认后节点上出现多个姓名 chip，画布摘要也显示多个人（界面与"单人"矛盾）。

## 2. 根因

| # | 位置 | 问题 |
| --- | --- | --- |
| 1 | `FlowDesigner.vue` 的选人弹窗 | **写死 `type="multiple"`**。共享组件的 `type` 决定 `el-checkbox-group` 的 `:max`（`single`→1 / `multiple`→999999），同时也决定「全选 / 取消全选 / 清空」是否渲染 |
| 2 | 写入口径 | `onUserPicked` 直接 `userIds = toUserIds(users)`，**不按 `multiMode` 收敛**；`normalizeAssignees()` 同样不看 `multiMode` |
| 3 | 切换多人方式 | `multiMode` 与 `userIds` 是两个独立字段：先**多选 3 人**再改成**单人**，3 个 chip 会一直挂着 |
| 4 | 编译期语义（真正的危害） | `SimpleFlowCompiler#renderUserTask`：指定人员 **1 人** ⇒ `flowable:assignee="<id>"`（任务直接派给他）；**>1 人** ⇒ `flowable:candidateUsers="a,b"`（**候选人抢单**，`ASSIGNEE_` 恒为 NULL，多人都能看到待办） |

> 第 4 条是这条缺陷"必须修"的理由：它不是"多显示了几个人"，而是**落库写单人、运行期变多人候选**。
> （源码位置：`ruoyi-vue-oa-master\ruoyi-workflow\src\main\java\com\ruoyi\workflow\simple\compile\SimpleFlowCompiler.java` 的 `renderUserTask` 分支，约 511-524 行。）

## 3. 修复（前端 2 个文件）

| 位置 | 改动 |
| --- | --- |
| `src/views/workflow/simple-flow/assigneeMapping.js` | 新增纯函数 `singleModeUserIds(multiMode, ids)`：先 `cleanIds`，`SINGLE` / 未设置 ⇒ 只留第 1 个；`AND/OR/SEQ` ⇒ 原样返回 |
| `FlowDesigner.vue` · 弹窗 | `type="multiple"` → `:type="userPickerType"`；`userPickerType` 取**打开弹窗时锁定的那个节点**（`pickerTargetNode`）的多人方式，单人 ⇒ `single` |
| `FlowDesigner.vue` · 确认写回 | `onUserPicked`：`userIds = singleModeUserIds(target.multiMode, toUserIds(users))` —— **不依赖界面**，旧数据 / 构造请求也挡得住 |
| `FlowDesigner.vue` · 切换即时收敛 | 新增 `onMultiModeChange`（挂在「多人方式」`el-radio-group` 的 `@change`）：多选→单人时**立刻**只留第 1 个人，并 `$message.warning` 明确告知"保留了谁、移除了谁" |
| `FlowDesigner.vue` · 加载归一化 | `normalizeAssignees()`：`multiMode=SINGLE` 却存了多人（历史脏数据）⇒ **内存里**用 `$set` 收敛成 1 个（不静默改库） |
| `FlowDesigner.vue` · 弹窗回显 | `pickerSelectedUsers`：单人节点只带第 1 个人进弹窗（否则会出现"勾着 3 个、确认后只剩 1 个"） |
| `FlowDesigner.vue` · 界面提示 | 「指定人员」与「多人方式」两处各加一行随模式变化的说明 |

口径一致性：**未设置 `multiMode` 按"单人"处理** —— 与编译器 `StringUtils.defaultIfBlank(multiMode, M_SINGLE)`
以及节点工厂 `newApprove()` 的默认值 `multiMode: 'SINGLE'` 完全一致。

## 5. 仍需人工点一次的部分（工具边界，见 `DEV-ENV.md` §6.53）

**"在共享弹窗里勾第 2 个人"这一步本桥点不中**：用户列表的 `el-checkbox`（`.user-card`）不进快照索引，
且超管账号 `user.dept.parentId === "0"` ⇒ 共享组件算出的初始 `deptId="0"` ⇒ 用户列表为空，
必须先点组织树里的部门（`el-tree` 节点同样不进快照索引）。

> 📌 **2026-10-05 更新（HANDOFF §3.7）**：列表为空这一半已经解决 ——
> 「指定人员」弹窗现在把**超级管理员**作为"常驻候选"固定显示在「用户列表」最前面
> （共享弹窗新增 `pinnedUsers`，超管走 `GET /system/user/{id}` 取回）。
> 也就是说**不需要先点组织树里的部门**就能看到可勾的人；但"勾选框本身点不中"仍是本桥的边界，勾选要人工点。

**人工确认步骤（约 1 分钟）**：
进任一流程设计页 → 点一个审批节点 → 「多人方式」保持**单人** → 「选择人员」→
左侧组织树点「研发部」→ 勾「王强」与另一位同事（预期：**勾第 2 个时勾不上**，`:max=1`）→
「确定」→ 抽屉与画布摘要只应出现 **1 个**人 →
再把「多人方式」切到「会签」→ 重开弹窗勾 2 人 → 「确定」→ 应出现 **2 个** chip（多人模式未被误伤的对照）。

> 反向对照（不需要界面）：即便绕过共享组件（旧数据 / 构造请求带回多人），
> `onUserPicked` 与 `normalizeAssignees` 也会把单人节点收敛成 1 个人 —— 这条由 §4 的 6 条单测直接锁定。

## 6. 未做的口子（记录，未扩大范围）

- **「角色」来源在单人模式下仍可多选**：`assigneeRoleIds` 是 `el-select multiple`。角色在编译期走
  `candidateUsers`（`ProcessConstants.ROLES`），单人节点选多个角色同样是"多人候选"的语义错位，
  但用户本次只指出「指定人员」。若要对齐，应在 `needLevel`/`assignee.source === 'ROLE'` 分支上加同样的收敛
  （建议作为独立小变更，**动共享面前先问用户**）。
- **发布校验（V-*）没有"单人节点人数 ≤ 1"的规则**：当前靠前端三层收敛（切换 / 确认 / 加载归一化）
  保证写入口径。若要彻底的"服务端也拦"，需要在 `SimpleFlowValidator` 里加一条规则并同步 `flow-regression` 断言。
