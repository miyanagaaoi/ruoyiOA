## 3. 四条测试流程（四个维度）

| # | defKey | 名称 | 覆盖维度 |
| --- | --- | --- | --- |
| 1 | `testSerial` | 测试01-串行审批（会签/或签） | 串行链 · **AND 会签** · **OR 或签** · 签名要求 |
| 2 | `testCondition` | 测试02-条件分支（排他路由） | **排他网关** · 中文等值条件 · **数值比较条件** · **兜底分支** |
| 3 | `testParallel` | 测试03-并行会审（多部门同时审） | **多实例并行** · 表单多选驱动 · 全部完成才合流 |
| 4 | `testCombo` | 测试04-组合（条件+并行+必经节点） | 串行 + 条件 + 并行 + **固定必经法务节点** |

### 3.1 testSerial — 串行审批

```
发起 → 部门负责人会签（张伟+超管，全部同意） → 分管领导或签（李娜+超管，一人同意即过） → 结束
```

验证点：会签必须**所有人都处理**才推进；或签**任意一人**处理即推进。

### 3.2 testCondition — 条件分支

```
发起 → 责任部门审批 → 类型路由（排他网关）
                        ├ 分支1：当 合同类型 = 经营    → 经发部审批
                        ├ 分支2：当 合同金额 > 10000   → 财务部审批
                        └ 其他情况（兜底）              → 行政审批
                      → 结束
```

验证点：**命中即走且只走一条**；两条都不命中走兜底；**条件同时为真时按优先级取第一条**（分支顺序即优先级）。

### 3.3 testParallel — 并行会审

```
发起 → 责任部门审批 → 会审部门（多实例，集合 = 表单的多选字段） → 结束
```

验证点：勾选 **N 个部门 → 同时产生 N 个待办**；全部处理完自动合流；**一个都不勾 → 自动跳过**；若变量不存在则报错（所以提交链路必须保证该字段始终写入，空数组也要写）。

### 3.4 testCombo — 组合

```
发起 → 部门负责人审批 → 类型路由
                          ├ 分支1：合同类型 = 经营 → 经发负责人审批
                          └ 其他情况              → 行政负责人审批
                      → 会审部门（多实例）
                      → 法务审批（固定必经，需签名）
                      → 结束
```

验证点：条件与并行**可共存且顺序正确**；法务作为主链固定节点**不受条件影响**（对应业务决策 Q4）。

### 5.2 编译产物（BPMN）结构

| 流程 | userTask | 排他网关 | 多实例 | 条件表达式 | default 流 |
| --- | --- | --- | --- | --- | --- |
| testSerial | 2 | 0 | 2 | 0 | 0 |
| testCondition | 4 | **1** | 0 | **4** | **1** |
| testParallel | 2 | 0 | **1** | 0 | 0 |
| testCombo | 5 | **1** | **1** | 2 | **1** |

**关键断言逐条核对**：

| 断言 | 结果 |
| --- | --- |
| 条件分支编译为**排他网关**（不是直接挂在 userTask 出口） | ✅ testCondition / testCombo 各有 1 个 `<exclusiveGateway>` |
| 表达式**整句包在一对 `${ }` 里**（写成 `${A} == 'B'` 运行期会报 non-Boolean） | ✅ `${contractType == '经营'}`、`${amount > 10000}` |
| 兜底分支编译为网关的 **default 流** | ✅ 各有 1 处 `default="..."` |
| 并行分支编译为**多实例用户任务**，集合 = 表单字段 | ✅ `flowable:collection="jointDepts"` |
| 多实例的分支值赋给审批人 | ✅ `flowable:elementVariable="dept"` + `assignee="${dept}"` |
| 会签完成条件 = 全部完成 | ✅ `${nrOfCompletedInstances == nrOfInstances}` |
| **或签完成条件 = 一人完成即可** | ✅ `${nrOfCompletedInstances >= 1}` |
| 条件里的中文**未被破坏** | ✅ 字节 `E7 BB 8F E8 90 A5` = 「经营」 |

> ⚠️ 核对中文时踩过一个坑：后端响应的 `Content-Type: application/json` **不带 `charset`**，
> PowerShell 的 `Invoke-RestMethod` 会按 Latin-1 解码，导致中文显示成乱码。
> 必须用 `Invoke-WebRequest` 取原始字节再显式 `UTF8.GetString`。
> 这**不是**系统缺陷（DB 与 BPMN 文件里的字节都是正确的），但说明接口对非浏览器客户端不够友好。

## 7. 如何用 API 重新获取 token（自动化用）

后端验证码是 **math 类型**且图形扭曲难以 OCR，脚本化调接口时用下面的方式（**用完必须恢复**）：

```powershell
# 临时关闭（DB + Redis 缓存都要改）
UPDATE sys_config SET config_value='false' WHERE config_key='sys.account.captchaEnabled';
redis-cli set "sys_config:sys.account.captchaEnabled" false
# 登录（口令需 RSA 加密：node tools\rsa-encrypt.js "admin123"）
POST /login  {"username":"superAdmin","password":"<密文>","code":"","uuid":""}
# 立即恢复
UPDATE sys_config SET config_value='true'  WHERE config_key='sys.account.captchaEnabled';
redis-cli set "sys_config:sys.account.captchaEnabled" true
```

创建数据时的另一个坑：**用 ID 匹配，不要用中文名匹配** —— API 响应的中文会被 PowerShell 按 Latin-1 解码，`$_.name -eq '中文'` 永远为假。
