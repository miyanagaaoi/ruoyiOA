## 第1章 项目背景与目标

### 1.1 背景

**V1（已完成）**：V1 PRD 规划的三项能力——**简化版流程设计器 / 表单打印 / 签名组件**——已全部落地代码（见 `doc/2.0/RuoYi现状勘察.md` §0 结论 1）。V1 的产物是"合同审批"这一条线跑通。

**2.0 的动因**来自四个具体问题：

1. **配置入口是散的**。新增一个审批单据要跑 **5 个纵向分段**的表单页（`UI/views/workflow/template/add.vue:1-45`），流程要去**另一个菜单**（`/workflow/simple-flow/designer`）单独设计，然后回到模板页**手工把 `defKey` 抄进下拉框**（`basic-info.vue:22-31`）。用户原话："直接把设计好的流程设计简易版移动到这里，自动绑定匹配"——即**消灭这次手工抄写**。
2. **谁都能发起任何单据**。`selectNewStartTemplateList` 只过滤 `del_flag` 与 `enable_flag`（`BE/.../mapper/template/TemplateMapper.xml:148-157`），**没有任何按人/按部门/按角色的可见性控制**；`submitScope` 在全仓 grep 零命中。用户原文要求的"谁可以提交该审批"与"流程管理员"都是**从零新建**的能力。
3. **打印模板有三套缺口**。打印子系统本身已完整（表/接口/配置页/预览页/日志都在），但**内置模板只有全局唯一一套**（`DEFAULT_TITLE = 集团合同类文件流转审批单`，`PrintServiceImpl.java:466`），且内置模板被前端**强制关掉签批栏**（`print/index.vue:182-200`）；而《集团资金审批单》的版式核心恰恰就是签批栏。
4. **合同与库存业务完全不在系统里**。合同台账、采购、销售、库存过账目前靠 `miyanagaaoi/contract`（CTMS）这套独立的 Python FastAPI + Vue3 系统，与 OA 之间**没有任何集成**：OA 里的"合同审批"批完，台账要人工再录一遍。

### 1.2 项目目标

| # | 目标 | 可衡量口径 |
| --- | --- | --- |
| G1 | **一次配置、四个页签** | 新建一个可用审批单据（含表单、流程、打印）**只在一个页面内**完成，页签内切换不计次；不再进入第二个菜单 |
| G2 | **流程自动绑定** | 保存/发布流程后，模板的流程引用**由系统回写**；人工填 `defKey` 的步骤从流程中消失 |
| G3 | **可见性可控** | 模板可配置"谁可以提交"（全员/指定人员/指定角色/指定部门），发起页据此过滤；未配置 = 全员（**与现状行为一致，保证存量不回归**） |
| G4 | **打印模板按单据类型可选** | 内置模板从 1 套扩展为 ≥3 套，且**按单据类型/模板**选定；签批栏不再被"内置"强制关闭 |
| G5 | **合同/采购/销售/库存进 OA** | 参考仓库 CTMS 的业务能力在 RuoYi 技术栈上重建，与 OA 的**账号、组织、角色、附件、审批流、打印**复用同一套底座，不再有第二套登录 |
| G6 | **零回归** | 存量模板、存量流程、在途单据、存量打印件在 2.0 上线后功能不回归（V1 的 AC-39 在 2.0 继续作为门禁） |

### 1.3 与 V1 PRD 的关系

- V1 PRD 仍是**合同审批二开**的规格来源，其 44 条 AC 继续有效。
- 2.0 PRD **不重复立项**已经落地的能力（简化设计器、打印子系统、签名组件、6 个二开控件）。`doc/2.0/RuoYi现状勘察.md` §7.3 给出了"2.0 不应重复立项的清单"，本 PRD 直接引用。
- 2.0 对 V1 产物的改动只有三类：**改结构**（模板页拆页签）、**补缺口**（submitScope / 绑定回写 / 内置打印模板）、**改语义**（模板编辑换 ID 的关联失联问题）。

## 第4章 需求一：表单定义四页签（B1）

### 4.1 目标与场景

**场景**：业务管理员要新增一个"资金审批"单据。现状要跑：① 模板配置 → 新增模板（5 个纵向分段，滚很久）→ ② 保存 → ③ **切到另一个菜单**「流程设计（简化版）」→ 新建流程 → 填 `defKey` → 设计节点 → 发布 → ④ **回到模板页**，把刚才那个 `defKey` **手工抄进「关联流程」下拉** → ⑤ 保存。

| --- | --- | --- | --- |

**保存顺序（冻结口径）**：

```text
① 页签 1 填完 → 点「保存草稿」→ 后端 upsert t_template（拿到 templateId）
```

## 第5章 需求二：可发起范围与关联审批（B1）

### 5.1 谁可以提交该审批（可发起范围）

**业务口径**：

- 范围类型 `0` 全员：与现状一致，**所有登录用户**在发起页可见可发起。
- 范围类型 `1` 指定人员：明细表登记 `user_id`；用户本人匹配即可见。
- 范围类型 `2` 指定角色：明细表登记 `role_id`；用户**拥有该角色**即可见（RuoYi 的 `sys_user_role`）。
- 范围类型 `3` 指定部门：明细表登记 `dept_id`；用户直属部门匹配即可见。**是否含下级部门？** → 建议**含**（RuoYi 部门树惯例），作为可配置开关 `include_child_dept`，默认含。**这是本 PRD 需要用户确认的第 2 个问题**。
- **叠加规则**：多条范围是 **OR**（满足任一即可见）。
- **管理员例外**：拥有 `workflow:template:list` 且 `superAdmin` 的用户不受范围限制（否则管理员会把自己锁在门外）。

**生效位置（两处，缺一不可）**：

| 位置 | 落点 | 要求 |
| --- | --- | --- |
| **列表过滤** | `TemplateMapper.xml:148-157` 的 `selectNewStartTemplateList` | 加 `submit_scope_type = '0' OR 命中明细表` 的条件；`TemplateServiceImpl.listNewStartTemplate:206-245` 传入当前 `userId/deptId/roleIds` |
| **发起兜底** | `flow-form` 的发起入口（`pageType=0` 落库前） | **服务端**再校验一次：无权限则 403。**不能只靠前端隐藏**（否则直接构造请求就能越权发起） |

> ⚠ **不要复用 RuoYi 的 `@DataScope`**：它只用在 5 处系统模块（`SysDeptServiceImpl:67` 等），与业务单表无关。参照 `DocViewGuard` + `AccessCheckMapper.xml` 的四路 union 范式自建（勘察报告 §6.3）。

### 5.2 关联审批控件（新增表单控件）

**用户原文**：*"增加表单控件，名称为关联审批，功能描述：管理员可以指定系统内表单，发起者根据范围选择自己已发起表单，审批人员点击后浮窗淡出指定表单"*。

**口径定稿**（用户已确认三项）：

| 项 | 定稿 | 说明 |
| --- | --- | --- |
| ① 管理员可指定的"系统内表单"范围 | **限定为已启用（`enable_flag='1'`）的模板** | 属性面板给下拉：只列已启用模板；支持多选（一个控件可关联多个候选表单） |
| ② 发起者可选的"范围" | **本流程所属分组（`t_template_type`）内、"自己已发起"的单据** | "自己" = `create_id = 当前用户`；"本分组" = 与被关联模板的 `type` 相同。**跨分组不可选** |
| ③ 审批人员点击后的浮窗 | **只读**展示该单据的**表单数据 + 审批状态** | 不含附件/正文/流程轨迹；不提供跳转（避免越权路径） |

**控件模型**：

```jsonc
{
  "__config__": { "label": "关联审批", "tag": "design-related-approval", "span": 24, "showLabel": true, "required": false },
  "__vModel__": "relatedApproval",
  "allowTemplates": ["<t_template.id>", "..."],   // 管理员指定，只能选已启用模板
  "multiple": true,                                // 是否允许关联多条
  "selfOnly": true,                                // 固定 true（口径②），留字段以备将来放开
  "sameGroupOnly": true,                           // 固定 true
  "displayFields": ["contractName", "amount"]      // 浮窗里额外突出的字段（可空 = 全字段按表单顺序）
}
```

**存储值**：`__vModel__` 在 `valData` 里存**被关联单据的业务ID数组**（`t_workflow_form.business_id` 或实例 id），形如 `["biz_xxx","biz_yyy"]`。**不存快照**——浮窗实时查（保证看到最新状态），但浮窗接口必须做**越权校验**（只能看自己有权的单据）。

**落地清单（一个控件要改 11 处，见勘察报告 §2.2）**：

## 第7章 需求四：合同管理、采购、销售、出入库（B3/B4）—— 移植方案与技术评审

### 7.1 评审结论（用户要求"合并功能还是直接引用对接接口需要评审"）

**评审对象**：`https://github.com/miyanagaaoi/contract`（CTMS，已克隆至 `.cache/contract-ref` 作只读基线）。

**客观事实**：

| 维度 | 参考仓库 CTMS | RuoYi-Vue-OA | 结论 |
| --- | --- | --- | --- |
| 后端 | Python 3 + FastAPI + SQLAlchemy + 自研迁移器 | Java 8 + Spring Boot 2.5 + MyBatis | **完全不同** |
| 数据库 | SQLite（可选 PostgreSQL） | MySQL 8 | **不同** |
| 前端 | Vue3 + Vite + Element Plus（54 个 `<script setup>`） | Vue2 + Vue CLI 4 + Element UI | **不同** |
| 账号/权限 | 自研 JWT + 代码常量权限点（99 个） | Spring Security + `sys_menu` 表 + `@PreAuthorize` + `@DataScope` | **重复能力** |
| 组织树 | `org_units`（物化路径） | `sys_dept`（`ancestors`） | **重复能力** |
| 附件 | 自研上传 + `object_type/object_id` 通用挂载 | `ruoyi-file` | **部分重复** |
| 编号 | 自研 `numbering_service` | `ruoyi-serial`（`ICodeGenService`） | **重复能力** |
| 打印 | 自研模板 + 内联 CSS 生成 HTML | `ruoyi-workflow/print`（模板表 + 日志 + A4 预览） | **部分重复** |
| 审批 | **单级**状态机（`draft→submitted→approved`） | Flowable 多级流程 | **语义不同** |
| 业务规模 | 39 表 / ~231 端点 / 后端 9,385 行 / 前端 35 视图 + 15 组件 10,358 行 | — | **大型** |

**方案对比**：

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **A. 独立部署 + 接口对接** | 零重写；CTMS 已在 UAT | ① 两套账号（用户要登录两次或做 SSO）② 两套组织/权限 ③ 数据割裂（合同在 CTMS、审批在 OA）④ 打印版式两套 ⑤ 运维两套（Python + Node 环境）⑥ 与"集团 OA 一体化"的诉求相悖 | ❌ 不推荐 |
| **B. 移植进 RuoYi（Java + Vue2 重写）** | ① 一套账号/组织/权限/附件/字典/编号/打印 ② 合同审批与台账天然打通 ③ 运维一套 | ① 工作量大（后端 XL、前端 XL）② Vue3→Vue2 与 Element Plus→Element UI 有**静默出错**风险点（`value-format` 15 处等）③ 精度与并发口径必须严格复刻 | ✅ **采纳** |
| **C. 先出接口契约，实现后置** | 边界清晰 | 用户已明确要求"移植进 RuoYi"，C 不满足诉求 | ❌ |

**用户决策**：**采用方案 B**。

### 7.2 移植的七条硬约束（不得"顺手优化"）

以下口径来自参考仓库已冻结的规格与注释，**凡与直觉冲突者一律以参考仓库为准**：

| # | 约束 | 为什么（证据） |
| --- | --- | --- |
| C-1 | **金额"先舍入再汇总"**：行金额先 `HALF_UP` 到 2 位，再求和 | BR-V2-13。Java 侧若先求和再舍入会产生 1 分钱差异，导出/打印/对账三方不一致（`doc_service.py:135,153-155`） |
| C-2 | **质保到期算法**：`生效日 + (期限−1) 个月 → 取该月最后一天`（2025-06-01 + 12 个月 → 2026-05-31） | `compute_warranty_end`（`models.py:77-85`）。反直觉，必须复刻 |
| C-3 | **「货品总额度」按 `biz_type LIKE '%入库%' AND NOT LIKE '%调拨入库%'` 筛选后 `SUM(qty_change*unit_price)`** | 注释明确警告**不能用 `qty_change>0` 判方向**（否则红冲无法冲减）。写成枚举白名单就会错 |
| C-4 | **库存类单据 `approved` 即终态，不使用 `completed`** | `models_doc.py:8`、`docs/12 §4.4` |
| C-5 | **库存不变式** `stocks.qty == SUM(stock_ledger.qty_change)`，并保留 `recalc` 运维接口用于校验修复 | `models_stock.py:6-7`（AC-V2-26） |

#### 7.2.1 S0 技术验证结论：`ruoyi-serial` 无法直接表达合同编号（F-8）

对 `ruoyi-serial` 源码的核实结论（该结论已写入 `oa-contract-ledger` 的 `design.md` D-6）：

| # | 缺口 | 证据 | 后果 |
| --- | --- | --- | --- |
| 1 | `RuleTypeEnum` 只有 `FIXED` / `DATE` / `SEQ` 三种 | `ruoyi-serial` 的枚举定义 | 无法表达"类型码 + 主体码 + 年度序"这种**多段组合 + 分段计数** |
| 2 | `DATE` 规则取**当前日期**格式化 | `CodeGenServiceImpl:112` | 无法按**合同签订日期**生成编号段 |
| 3 | `SEQ` 按 `confId` 单一计数 | 同上 | 一个计数器无法同时服务"类型码 + 主体码"的多个桶 |
| 4 | 年度重置由**定时任务**在 1 月 1 日触发 | `CodeConfigServiceImpl:162-189` | 当天未运行则**不重置**，序号会跨年延续 |

**处置（REQ-CTMS-006 的落地口径）**：优先尝试"纯配置路线"；不可行时做**向后兼容的最小扩展**——
① 支持"业务参数分桶"（调用方按类型码/主体码传参）；② 年度重置改为**惰性重置**（按编号前缀检测年份变化）；③ 允许调用方**指定参考日期**（用签订日期而非当前日期）。
验收判据（4 条）与实施任务见 `oa-contract-ledger` 的 `tasks.md` 1.2 / 1.3。

> 因此批次变更集把"对平台能力的依赖"写成 proposal 里的显式依赖声明，行为契约由自身新能力承载；
> 待总纲归档后，再由后续变更集收敛为 `MODIFIED`。

### 15.2 规范约束

1. **规划边界**：`openspec-propose` 工作流**只产出规划件**（`proposal.md` / `specs/**/spec.md` / `design.md` / `tasks.md`），**不改代码**。实现必须由用户显式发起 `openspec-apply-change`。
2. **能力路径**：新能力放 `openspec/specs/<capability>/spec.md`；本项目的既有能力路径遵循 `<域>/<能力>`（如 `workflow/form-definition`）。
3. **增量规格**：delta spec 写 `ADDED` / `MODIFIED` / `REMOVED`，不复制主规格。
4. **验收可追踪**：`tasks.md` 的每一项任务必须能映射到本文件的 `REQ-*` 与 `AC-*`。
5. **归档**：全部批次验收通过后 `openspec archive`，并把结论回写到本文件的版本记录。
