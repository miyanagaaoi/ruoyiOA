## 1. 背景与缺陷机理（为什么必须有防线）

| 绑定链 | 存在哪 | 谁去改它 |
| --- | --- | --- |
| 流程 `t_flow_simple.content.formId` | 设计器 JSON 里的一个字段 | **没人改** ← 缺陷所在 |
| 模板 `t_template.form_id` | 模板表的一列 | `TemplateMapper.xml#repointFormId`（表单保存时自动改指） |
| 表单行 `t_template_dynamic_form.id` | 每次保存**换新 id**（旧行 `enable_flag='0'`） | `TemplateDynamicFormServiceImpl#updateTemplateDynamicForm` |

- 设计器的字段清单取**流程内容里的 `formId`**；发起页/运行期取**模板的 `form_id`** ⇒ 两条链一旦分叉就是
  "界面显示 A、校验按 B"（上一轮实测：条件引用 `contractType/amount`，界面却显示 `field101`）。
- 上一轮（10-05）**只对齐了数据**：`doc/缺陷-流程条件字段与关联表单错位.md` §7-B 明确写着
  "一致性检查 / 表单保存时反向校验 **本轮未做**，建议作为独立小变更" —— 本任务就是把它做掉。

## 3. 实现

### 3.1 一致性检查：**只读巡检接口**（HANDOFF §11-8）

**接口**：`GET /workflow/simple-flow/form-consistency`（权限点沿用 `workflow:simpleFlow:query`，超管可用）

```jsonc
{ "code": 200, "data": {
  "scannedFlows": 2, "scannedTemplates": 13,
  "issueCount": 12, "highCount": 0, "mediumCount": 12, "lowCount": 0,
  "issues": [
    { "kind": "MISMATCH", "severity": "high", "subject": "flow",
      "flowId": "...", "defKey": "htsp", "flowName": "合同审批", "flowStatus": "1",
      "templateId": "B9B72AB7…", "templateName": "合同审批", "templateEnableFlag": "1",
      "flowFormId": "564FA25A…", "templateFormId": "557…",
      "detail": "流程内容 formId=… 与模板 form_id=… 不一致 —— 设计器按流程里的表单出字段、发起页按模板的表单出字段，两边会各说各话" },
    … ]}}
```

**覆盖的 8 类问题**（每条都带 flowId / defKey / templateId，可直接定位）：

| kind | 严重度 | 判据 |
| --- | --- | --- |
| `MISMATCH` | high | 流程 `content.formId` ≠ 绑定模板 `form_id`（**本次要抓的主角**） |
| `FLOW_FORM_MISSING` | high / medium | 流程引用的表单行不存在（没配 formId 记 medium） |
| `FLOW_FORM_DELETED` | high | 流程引用的表单行已软删（`del_flag=1`） |
| `FLOW_FORM_DISABLED` | high | 流程引用的表单行已停用（`enable_flag=0`） |
| `CONDITION_FIELD_INVALID` | high | 条件字段/并行分支字段在其引用表单里**不存在或未设为必填**（V-8 运行期口径） |
| `TEMPLATE_FORM_BAD` | 启用模板 high / 停用模板 medium | 模板 `form_id` 指向不存在/已删/已停用的表单行 |
| `TEMPLATE_NO_FORM` | low | 模板 `form_id` 为空（发起页取不到表单） |
| `TEMPLATE_DANGLING_FLOW` | medium | 模板 `simple_flow_id` 指向的流程不存在或已删 |

**为什么做成"巡检接口"而不是"发布前阻断"**（形态选择理由，已报队长认可）：

1. 错位是**表单保存那一刻**造成的，不是发布那一刻 —— 在发布链路上拦，**治不了源头**；
2. 更糟的是会**把存量数据变成拦路虎**：库里本就有 6 条模板指向已停用/已软删的表单行（§7-C 的存量，
   属用户待决策的清理项），发布前阻断会让这些流程**再也发不出去** —— 用误报换安全感；
3. 巡检接口**只读**，可随时跑（发布前 / 门禁 / 排障），不会因为一条历史脏数据把业务卡死；
4. 源头那一侧由 §3.2 的 PRD V-8 反向校验**阻断**，两者一个治源头、一个扫存量，口径落在同一份数据上。

**误报边界（有意为之）**：

- 只扫**未删除**的流程与模板（`del_flag='0'`）；
- **独立发布的流程**（没有 `simple_flow_id`，也没有同 `def_key` 的模板）**不产生 MISMATCH** —— 模板可后补是既有合法状态（`SimpleFlowServiceImpl#syncNodeFieldAuth` 同口径）；
- 已**停用**的模板只报 medium/low：它不参与发起，属"该清理的存量"而不是"正在流血"；
- **草稿流程**也只降级报告（草稿本来就允许与表单不一致）；
- 绑定口径**两种都认**：`t_template.simple_flow_id`（新）与 `t_template.def_key`（旧/独立发布后绑的），避免漏报。

### 3.2 PRD V-8 反向校验：**阻断在写库之前**（HANDOFF §11-9）

落在表单保存路径 `TemplateDynamicFormServiceImpl#updateTemplateDynamicForm`（任何调用方都绕不过），
判定逻辑在 `FormV8Guard`：

| 情况 | 行为 |
| --- | --- |
| **已发布**流程（`status=1`）的条件字段 / 并行分支字段在新内容里**不存在或未设为必填** | **阻断**（`ServiceException`，body `code=500`），文案列出流程 + 字段 + 原因 —— PRD V-8 原文口径 |
| 字段仍成立，但流程指向的正是"即将被替换的旧表单" | **放行** + 响应回 `formFlowWarnings[]`（前端 `msgWarning` 显示）+ 服务端 `WARN` 日志 —— **不得静默** |
| **草稿**流程字段失效 | 只告警（草稿还没生效，PRD 的"阻断"针对已生效流程） |
| 新内容**解析失败** | 只告警"未做字段级校验"（一次坏 JSON 不能误伤所有流程） |
| 容器里没有 `FlowFormUsageProvider`（如只装 template 模块做单测） | 跳过校验 + `WARN` 日志（不让模块化装配/单测保存不了表单） |

**跨模块方案（避免循环依赖）**：接口 `com.ruoyi.template.spi.FlowFormUsageProvider` 放在 ruoyi-template，
实现 `SimpleFlowFormUsageProvider` 放在 ruoyi-workflow（流程表与解析口径都在那边）。
模块依赖本来就是 `ruoyi-workflow → ruoyi-template`，反向直接调用会成环，故做接口倒置。

## 5. 顺带修掉的两个既有问题（真发现，非本轮引入）

### 5.1 `ruoyi-template` 模块的测试阶段**一直编译不过**（已修）

- 现象：`mvn -B -pl ruoyi-template test` 报

  之所以长期没人发现：日常打包走的是 `mvn -pl ruoyi-admin clean package`（**不带 `-am`**，子模块依赖取本地仓库的 jar），
  谁都没跑过这个模块的 test 阶段。
- 处置：补齐三个桩方法（语义与真实 Mapper 一致）。**此前无人跑过该模块测试阶段** —— 本轮新增的 15 条是该模块

### 5.2 PowerShell 的 `(Sql "…")[0]` 陷阱（写验收脚本的人都会踩）
