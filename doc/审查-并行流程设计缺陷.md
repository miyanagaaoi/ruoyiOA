# 飞书审批「并行分支」设计缺陷审查

> **审查对象**：`doc/参考文档/wireframes.html`（飞书审批设计器低保真原型，S03 / S03A / S03B / S07）
> **交叉验证**：飞书审批后台实时页面（合同审批（含用印）草稿，`createApproval?id=7464107468755484700`）
> **审查目的**：① 判断该设计能否直接照搬；② 提炼我方简化流程设计器必须规避或显式定义的点
> **审查日期**：2026-10-03

---

## 0. 结论摘要

**不是"不能用"，而是"同一套 UI 承载了两种互斥语义，且兜底规则若隐若现，会产生静默错误"。**

| 级别 | 编号 | 缺陷 | 后果 |
| --- | --- | --- | --- |
| **根本** | F1 | 一个"并行分支"容器同时承担 **XOR（选一条）** 与 **AND（同时走多条）** 两套语义 | 管理员无法预知单据会同时给几个人 |
| **根本** | F2 | 「条件分支」与「并行分支」在画布上**长得完全一样** | 同样一句"当 合同类型 等于 经营"，语义可能完全不同 |
| **高危** | F3 | 分支**不设条件 = 恒真**，会吃掉「其他情况」兜底 | 应审部门被**静默跳过**，审批链缺环节 |
| **高危** | F4 | **合流语义完全未定义**（等全部？等任一？） | 真并行时下游节点可能提前推进 → 漏审 |
| **高危** | F5 | 分支内**同一审批人重复出现**，被"去重"规则静默自动同意 | 管理员以为审了两轮，实际只审一轮 |
| **高危** | F6 | 并行分支下的**驳回 / 退回 / 撤回**语义缺失 | 在途任务悬挂、意见丢失、重提后重复审批 |
| 中 | F7 | 条件字段的「必填」约束**跨向导步骤耦合** | 回第 2 步改表单，第 3 步的条件被静默废掉 |
| 中 | F8 | 同一自然人出现在多条并行分支时，去重语义未定义 | 兼任两个会审部门 → 双待办或静默跳过 |
| 中 | F9 | 「其他情况」标注"不可编辑"有歧义 | 误以为车道内的审批节点也不能改 |
| 低 | F10 | 缺分支数量上限、空分支、分支命名与排序规则 | 边界行为未知 |
| 低 | F11 | 限时审批 / 催办 / 自动化在分支下的作用域未定义 | 超时提醒与"流程通过"触发点不明 |
| 低 | F12 | **原型自身**：分叉/汇合线写死 2 条分支 | 加到 3 条分支线就错位，不能直接当视觉基线 |

## 1. 先还原真实语义（避免冤枉它）

从实测页面还原出的流程（与原型 S03 一致）：

```
提交
 └ 审批（直属部门负责人）
     └── 并行分支容器 ──────────────────────────────┐
     │   并行分支 1    当 合同类型 等于 经营          │
     │     └ 审批（经发负责人）                       │
     │   其他情况（系统兜底）                          │
     │     └ 审批（行政）→ 审批（法务）→ 审批（行政）  │
     │        → 审批（财务）→ 审批（副总经理）          │
     └────────────────────────────────────────────┘
         └ 抄送 → 办理盖章上传备案 → 结束
```

**关键观察**：容器里只有两条车道，一条带条件、一条是兜底。两条车道**互斥**——`合同类型=经营` 时走车道 1，否则走「其他情况」。**这个配置下永远只有一条分支被执行，"并行"从未发生。**

而原型 S03B 的插入菜单却把这个节点标注为 **"多分支同时流转"**（`wireframes.html:391`），S03A 的容器头也写着 **"每个分支可各自设置进入条件"**（`:329`）。**这两句话是矛盾的。**

> 平心而论：带条件的并行 + 排他兜底，在数学上是可以自洽的——
> `其他情况 = NOT(分支1条件 OR 分支2条件 OR …)`，各分支条件为真者并行执行。
> **问题不在语义不可实现，而在 UI 把两件事混在一起说，且兜底规则只在一个注释里出现。**

## 2. 缺陷详述

### F1【根本】一个容器，两套语义

- **证据**：`wireframes.html:329`「并行分支 / 每个分支可各自设置进入条件」；`:391`「并行分支 —— 多分支同时流转」；`:357`「其他情况…其他条件都不满足时进入」。
- **问题**：「其他情况」是**排他网关的 default flow** 概念（有且仅有一路）；"各分支同时流转"是**并行网关**概念（多路同时）。二者被塞进同一个容器、同一个名字。
- **影响**：管理员配完不知道会发生什么。上图这个配置里"并行"是假的（永远单路）；但只要有人把车道 1 的条件去掉，行为立刻从"单路"变成"多路"，**而界面上不会有任何提示**。
- **建议**：
  1. **拆成两个节点类型**——「条件分支（选一条）」与「并行分支（全部执行）」，图标、容器描边、菜单文案全部区分；
  2. **「其他情况」只属于条件分支**；并行分支不设兜底（并行不需要防卡死，因为至少有一条恒真或全部跳过需另行定义）。

### F2【根本】两种节点在画布上无法区分

- **证据**：对比 S03A（并行，`:328-347`）与 S07（条件，`:552-555`）——用的是**同一套 `branch` + `lane` + 「其他情况」**结构，唯一差别是容器头文案和条件 chip。
- **问题**：条件 chip「当 合同类型 等于 经营」在两种容器里长得一样，含义却相反（选一条 vs 可能同时走多条）。
- **建议**：容器改用不同形态表达语义——条件分支用**分叉箭头**，并行分支用**并排泳道 + 上下横杠**；条件 chip 统一前置"（满足则进入本分支）"与"（满足则**同时**执行本分支）"的差异化文案。

### F3【高危】不设条件的分支会"吃掉"兜底

- **证据**：参考件 §4.3 记载并行分支「**默认所有表单都可进入**，也可设条件」；原型 `:244`/`:329` 的"每个分支可各自设置进入条件"暗示条件是可选的。
- **推理**：车道不设条件 ⇒ 条件恒真 ⇒ `其他情况 = NOT(其他分支条件)` 恒假 ⇒ **兜底车道永不执行**。
- **影响**：本例中兜底车道承载的是"行政→法务→行政→财务→副总经理"整条链——一旦管理员新增分支时漏配条件，**这 5 个审批节点会全部消失**，且系统不会报错、不会告警。
- **建议**：
  1. 新增分支时**条件必填**，或对"无条件分支"给出显式名称「其他情况（默认执行）」并**自动置灰真正的兜底车道**；
  2. 发布校验：若存在无条件分支且兜底车道内有节点 → **阻断发布**并提示"该分支将导致兜底分支永不执行"。

### F4【高危】合流语义未定义，且画法传达了错误的心理模型

- **证据**：`wireframes.html:326-349` 用 `split` / `stubs` / `merge` 三段表达"分叉—汇合"，`merge-bar` 画在两条车道下方，视觉上表示"两条都完成才继续"。
- **问题**：
  1. 本例中两条车道**互斥**，永远只有一条执行 —— 画法与行为相反；
  2. 若真出现多车道同时执行，**"合流等谁"在页面上没有任何配置项**：等全部完成？等任一完成？先完成的是否作废其他？
- **影响**：真并行场景下，下一个节点（法务）可能在某分支尚未审批时被推进 → **漏审**；或相反，某个分支无人处理导致单据永久卡住。
- **建议**：合流规则**必须成为显式配置项**（全部完成 / 任一完成即继续并作废其余），并在画布上标注（如"汇总：等待全部 3 条分支"）。

### F5【高危】分支内同一审批人被"去重"静默自动同意

- **证据**：实测流程的其他情况车道为 `行政 → 法务 → 行政 → 财务 → 副总经理`（两次"行政"）；`wireframes.html:308` 与其对应的实测提示为"若同一审批人在流程中重复出现，**默认只审批一次**"。
- **影响**：第二个「行政」节点的审批会被系统自动同意。若业务意图是"行政初审 + 行政复核"，则**复核环节事实上不存在**，且流程记录上会显示为"已通过"，事后审计极难发现。
- **建议**：发布校验对"同一审批人/角色在**同一条分支内**重复出现"给出**警告**（不是静默去重），并提供"强制每次都审"的开关。

### F6【高危】并行分支下的驳回 / 退回 / 撤回语义缺失

- **证据**：原型与实测页面均未出现相关表达；S03A 只画到"分支汇合后继续"。
- **必须定义的行为**：
  1. 某分支**驳回**时，其余在途分支的任务是**自动取消**还是**继续执行**？已产生的意见是否保留？
  2. 某分支**退回**发起人后重提，**已完成的其他分支**是否重新生成、已签的签名是否失效？
  3. **提交人撤回**时，多分支在途任务如何取消？
  4. 分支内某个审批人**转办/加签**后，是否影响合流判定？
- **影响**：这正是引擎层最容易出 bug 的地方。我方引擎已有明确硬约束：**并行网关前必须唯一用户任务，多对多时无法撤回**（PRD `5.5 P-8`）。
- **建议**：把这 4 条写成验收标准（AC），并在设计器上用提示气泡明示。

### F7【中】条件字段的「必填」约束跨向导步骤耦合

- **证据**：`wireframes.html:359`「可用作条件的字段，必须先在**表单设计**中设为必填」；`:585` 同义。
- **问题**：表单设计是**向导第 2 步**，流程设计是**第 3 步**。约束只在第 3 步配置条件时检查一次；之后回到第 2 步把该字段改成非必填、或直接删掉字段，**第 3 步的分支条件不会被反向校验**。
- **影响**：运行期条件字段取到空值 → 条件恒假 → **静默全部落入兜底分支**，审批链整体走错。
- **建议**：① 发布时校验"条件引用的字段仍存在且为必填"；② 表单设计保存时**反向扫描**所有引用该字段的流程并阻断/告警。

### F8【中】同一自然人出现在多条并行分支时的去重语义未定义

- **场景**：一人兼任经济、行政两个会审部门的负责人（我方场景很常见）。
- **问题**：去重规则是为**串行重复**设计的；并行重复时，是产生两个待办、还是只产生一个、还是后者被自动同意？无定义。
- **建议**：默认**产生两个待办**（并行语义优先），并在待办列表用"会审·经济 / 会审·行政"区分。

### F9【中】「其他情况」标注"不可编辑"存在歧义

- **证据**：`wireframes.html:357`「「其他情况」是系统兜底分支：不可编辑、不可删除」。
- **问题**：不可编辑的是**车道自身的条件**；但实测页面里该车道**内部挂着可编辑的审批节点**（审批人：行政，`:343`）。标注容易被读成"整个车道都不能动"。
- **建议**：文案改为「该分支的**进入条件**由系统维护，不可编辑；分支内的节点可正常配置」。

### F10–F11【低】边界与作用域表达缺失

- **F10**：无分支数量上限、无"空分支"（有车道无节点）行为说明、无分支排序/优先级规则。
- **F11**：`限时审批`（`:664`）、`催办`、`自动化`（`:719`）在分支/并行下的作用域未定义——按**节点**还是按**分支**计时？"流程通过"在什么时候算通过（全部合流后？）？

### F12【低，但影响我们】原型自身的技术缺陷

- **证据**：`wireframes.html:67` `.split-bar{left:25%;right:25%}`、`:72` `.merge-bar{left:25%;right:25%}`，且 `stubs` 固定写死 **2 个** `<span>`（`:242`、`:261`、`:327`、`:348`）。
- **问题**：这套画法**只能表达 2 条分支**。一旦点「+ 添加并行分支」变成 3 条，分叉横杠与竖直短线将与泳道**错位**。
- **影响**：如果拿这张原型当视觉基线交付前端，会直接把缺陷带进产品。
- **建议**：分叉/汇合线改为**按泳道数量动态计算**（或改用 `border-top` + 伪元素按 `flex` 均分）。

## 3. 对我方简化流程设计器的硬性要求

> 我们的设计器（PRD 第 6 章、原型 S1 / S14–S16）已避开一部分，但需要把下面几条**写死**。

| # | 规则 | 对应缺陷 |
| --- | --- | --- |
| R1 | **「条件分支」与「并行分支」是两个节点类型**，图标/文案/画法必须可区分；条件分支 = 选一条 + 系统兜底；并行分支 = 全部执行，**不设兜底** | F1、F2 |
| R2 | **并行分支的合流规则必须显式配置**：`全部完成才继续`（默认）/ `任一完成即继续，其余分支作废` | F4 |
| R3 | **条件分支的「其他情况」自动生成、不可删**；并行分支不出现该车道 | F1 |
| R4 | **条件字段必须存在且为必填**：发布时校验；表单设计保存时反向校验 | F7 |
| R5 | **同一审批人在同一条分支内重复出现 → 发布警告**，不得静默去重 | F5 |
| R6 | **同一人出现在多条并行分支 → 产生多个待办**，并在待办与打印件上以分支名区分 | F8 |
| R7 | **驳回 / 退回 / 撤回在并行下的行为写成验收标准**（其余分支任务作废、意见保留、重提后分支全部重生成） | F6 |
| R8 | **分支必须有名字**（默认「分支 1/2/…」），名字要出现在待办环节名与打印件签批栏标题上 | F10 |
| R9 | **分支数量上限**（建议 5）+ 超限提示；空分支（无节点）在发布时报错 | F10 |
| R10 | 超时提醒**按分支独立计时**；自动化触发点明确为"全部合流并通过后" | F11 |
| R11 | 我方采用的「多实例 + 表单多选字段」方案**天然规避 F1–F4**：分支数由数据决定、无兜底车道、合流即多实例完成条件 —— 继续沿用 | F1–F4 |

## 4. 业务决策记录（2026-10-03 已确认）

| # | 问题 | 结论 | 落地方式 |
| --- | --- | --- | --- |
| Q1 | 会审部门并行时，是"每个被选部门都必须审完"还是"任一部门审完即可"？ | ✅ **全部**：每个被选部门**都必须审完** | 多实例完成条件 = `${nrOfCompletedInstances == nrOfInstances}`；"任一完成即继续"仅作为**可选配置**保留，不作默认 |
| Q2 | 某支驳回后，其余分支已提交的意见是否保留在办理过程里？ | ✅ **保留** | 其余分支任务置为"已作废"，但 `flowCmts` 意见记录**不删除**，办理过程**只读展示**；驳回理由单独留痕 |
| Q3 | 同一人兼任两个会审部门时，是否需要"合并为一个待办、一次审完两个部门"？ | ✅ **不合并**；改为**预留配置项**："当审批人为同一人时，是否自动通过" | 设计器节点配置新增开关（默认**每次都审**＝不自动通过）；引擎侧去重实现与该开关同期交付（P1，`REQ-FLOW-006`） |
| Q4 | 会审部门为"法务"时是否需要强制走（不可由提交人不勾选）？ | ✅ **不预置系统规则**：由**流程管理员在具体流程中固定**（固定节点 / 固定分支） | 系统只提供"固定节点/固定分支"能力，不内置"哪些合同必须法审"的判断；合同审批流程模板里法务作为**主链固定审批节点**，且提交人的"其他会审部门"多选**不含法务** |

> **Q4 的设计含义**：把"要不要送法审"这个判断留在**流程配置**里（管理员职责），而不是交给提交人勾选，也不是写死在系统字典里。这样同一套代码既能表达"合同必送法务"，也能表达另一种单子"不送法务"，无需改代码。

### 决策带来的连带影响

| 影响点 | 说明 |
| --- | --- |
| 待办生成 | 同一人兼任两个会审部门 → 仍产生**两个待办**（Q3），由"是否自动通过"开关决定第二个是否被自动处理 |
| 任务作废状态 | 需新增任务状态"已作废"（并行分支驳回场景，Q2），并保证作废任务**不出现在待办、但意见在办理过程可见** |
| 打印件 | 作废分支的签批栏**仍打印**（意见已留痕），并标注"（已作废）"；未到达的节点才是空栏 |
| 流程模板 | 合同审批模板 = 主链固定节点（含法务）+ 动态并行会审（经营/经济/人力/行政，由表单多选驱动） |
