# 缺陷报告 · 会签/或签节点的多实例集合变量缺失

> **发现日期**：2026-10-04　**发现方式**：真实业务模拟（API 发起 → 多账号审批）
> **严重级别**：**阻塞** —— 会签节点无法使用；位于首位时流程无法发起
> **状态**：已定位根因，**未修复**

---

## 1. 现象

走 `testSerial`（`start → 部门负责人会签(AND) → 分管领导或签(OR) → end`）：

```json
POST /workflow/handle/startFlow  { "templateId": "<testSerial 模板>" }
→ HTTP 200  {"msg":"流程启动失败，请联系管理员","code":500}
```

**流程连启动都失败。**

改把会签挪到第二位（`testSerial2`：`start → 预审(单人) → 会签(AND) → end`）：

```json
startFlow                → code=200 成功，首任务「预审（单人）」
提交预审                  → code=200
→ 但会签节点没有生成任务，预审任务仍挂在待办里（流程卡住）
```

---

## 2. 根因（后端日志原文）

```
org.flowable.common.engine.api.FlowableIllegalArgumentException: Variable 'n1_approval' was not found
    at org.flowable.engine.impl.bpmn.behavior.MultiInstanceActivityBehavior.resolveAndValidateCollection(...)
    at ...ParallelMultiInstanceBehavior.createInstances(...)

com.ruoyi.common.exception.base.BaseException: 异步处理失败:Variable 'n2_approval' was not found
    at com.ruoyi.mq.consumer.AsyncTaskConsumeService...
```

编译器为会签/或签节点生成的多实例是这样的：

```xml
<userTask id="n1" name="部门负责人会签" flowable:assignee="${assignee}" ...>
  <multiInstanceLoopCharacteristics isSequential="false"
      flowable:collection="n1_approval"        <!-- ← 这个变量没人创建 -->
      flowable:elementVariable="assignee">
    <completionCondition><![CDATA[${nrOfCompletedInstances == nrOfInstances}]]></completionCondition>
  </multiInstanceLoopCharacteristics>
</userTask>
```

**`n1_approval` / `n2_approval` 这类「`{节点id}_approval`」变量在整个系统里没有任何地方创建。**

RuoYi-OA 的运行时确实会在**完成当前任务时**为下一环节准备参与人变量
（`FlowHandleServiceImpl.completeTask` 里的注释：
*"处理委托，特别处理下个环节处理人为固定人员的情况"* → `handleEntrustAfterNextTask`），
但实测它**并不创建** `{nodeId}_approval` 这个约定名。

### 影响分两种情况

| 会签节点位置 | 后果 |
| --- | --- |
| **首节点**（紧跟发起） | **流程启动直接失败**，用户看到「流程启动失败，请联系管理员」 |
| **非首节点** | 上一节点提交后**异步处理失败**，流程卡在半路，上一节点的任务仍挂在待办里 |

---

## 3. 为什么这是"契约缺口"而不是"配置问题"

编译器的意图很清楚：**用 `{nodeId}_approval` 承载该节点的参与人列表**，
由运行时按节点的 `flowable:userType` / `flowable:dataType` 扩展属性解析后注入。

而单人会签（`multiMode=SINGLE`）走的是另一条路 —— 编译器直接内联：

```xml
<userTask id="n1" flowable:assignee="superAdmin" flowable:userType="assignee" flowable:dataType="fixed">
```

**单人能跑通、多人跑不通**，说明两条路径只有一条真正打通了。

### 决定性证据（已核实）

1. **`_approval` 这个字符串在整个后端只出现一次** —— 就是编译器自己那一行：

   ```
   \ruoyi-workflow\...\SimpleFlowCompiler.java L506:
       appendMultiInstance(sb, sequential, e.id + "_approval", "assignee", completion);
   ```

   **运行时代码里没有任何地方产生这个名字。**

2. **项目既有的 BPMN 设计器产物里也没有会签可参考**。把已部署的 `flow_jq4xok98`
   （用自带 BPMN 设计器做的「测试流程」）从 `ACT_GE_BYTEARRAY` 抠出来看，
   整个流程**只有一个 userTask**：

   ```xml
   <userTask id="Activity_129acej" name="test" flowable:assignee="superAdmin" .../>
   ```

   没有多实例、没有 `collection`、没有会签约定。

**结论：`{nodeId}_approval` 是编译器凭空发明的约定，本项目从未实现过它。**

## 4. 修复方向（三选一，需产品/架构拍板）

### 方向 A（推荐 · 自包含）：编译器附带一个「启动时注入」监听器

在 `<process>` 上挂一个 start 执行监听器，**流程启动时一次性把所有会签节点的参与人列表写成变量**：

```xml
<process id="testSerial" isExecutable="true">
  <extensionElements>
    <flowable:executionListener event="start"
        class="com.ruoyi.workflow.simple.compile.ApprovalUsersInitListener"/>
  </extensionElements>

  <userTask id="n1" name="部门负责人会签">
    <extensionElements>
      <flowable:properties>
        <flowable:property name="approvalUsers" value="superAdmin,58FE8668233B422FB69EE575F5F402A5"/>
      </flowable:properties>
    </extensionElements>
    <multiInstanceLoopCharacteristics isSequential="false"
        flowable:collection="n1_approval" flowable:elementVariable="assignee"/>
  </userTask>
```

监听器里读 `BpmnModel`，把每个带 `approvalUsers` 属性的节点解析成列表并
`setVariable(nodeId + "_approval", list)`。

| 优点 | 代价 |
| --- | --- |
| **自包含** —— 不依赖 RuoYi 运行时配合，不动既有代码 | 需在 `ruoyi-workflow` 新增约 40 行监听器类 |
| **同时覆盖"首节点是会签"** —— 启动即注入，不需要"上一节点"触发 | — |

### 方向 B：运行时补齐变量

在 `FlowHandleServiceImpl` 的 **startFlow 与 completeTask 两条路径**上，进入节点前注入。

- ⚠️ 首节点是会签时，"完成上一节点"这条路径**根本不会被触发**，必须单独处理启动路径
- ⚠️ 改的是既有运行时代码，**回归面更大**（影响 BPMN 设计器做出来的所有流程）

### 方向 C（保底）：会签不用多实例

改为「并行网关 + 每人一个用户任务 + 网关 join」，每个任务的 assignee 直接内联。

- ✅ 完全不依赖变量注入
- ⚠️ BPMN 节点数随人数线性增长
- ⚠️ **或签（任一完成即走）无法用并行网关表达**，需另行处理（可退回 `candidateUsers` 单任务语义）

## 5. 复现步骤

```powershell
# 首位会签 → 启动即失败
POST /workflow/handle/startFlow  { "templateId": "<testSerial 模板ID>" }
# → {"msg":"流程启动失败，请联系管理员","code":500}
# 后端日志：Variable 'n1_approval' was not found

# 非首位会签 → 卡在半路
POST /workflow/handle/startFlow  { "templateId": "<testSerial2 模板ID>" }   # 成功
POST /biz/flow/submit            { "operateType":"200", "flowTask": {...n1 预审...} }
# → 会签节点不生成任务，n1 任务仍在；日志：异步处理失败:Variable 'n2_approval' was not found
```

## 6. 顺带发现：任务完成是**异步**的

排查时从日志里看到：

```
c.r.m.c.AsyncTaskConsumeService - 异步处理消息异常
msg={"beanName":"flowAsyncService", ...}   exchange: flow.exchange
```

**任务完成经由 RabbitMQ 异步消费。** 这有两个直接后果：

1. **不能用"提交后立刻查库"来断言结果** —— 我前面测并行会审时看到的任务数
   「4→4→3→2」就是这个原因造成的，当时误判为"事务提交竞态"，实际是**异步消费未完成**。
   正确做法是提交后轮询等待（或订阅完成后的事件）。
2. **异步失败时用户只看到"提交成功"** —— 会签那次提交返回 `code=200`，
   但流程实际卡住，异常只落在后端日志里。**这是可观测性缺口**：
   用户以为提交成功了，单据其实没往下走。

## 7. 影响面

| 功能 | 是否受影响 |
| --- | --- |
| 单人会签 / 或签（`multiMode=SINGLE`） | ✅ 不受影响（内联 assignee） |
| **多人会签（AND）** | ❌ **不可用**（集合变量缺失） |
| **多人或签（OR）** | ❌ **不可用**（同上） |
| 多人依次审批（SEQ） | **需复测**（推测同样走多实例） |
| 并行会审 | ⚠️ 任务能生成（集合来自表单字段，用户已填），但 `joinMode=ALL` 不合流（见另一份报告） |
| 条件分支 / 串行单人 | ✅ 正常 |

## 8. 与另一份缺陷报告的关系

| 报告 | 缺陷 | 共性 |
| --- | --- | --- |
| 本报告 | 会签节点的 `{nodeId}_approval` 变量缺失 | 都出在**多实例**上 |
| [`缺陷-并行会审全部完成不合流.md`](缺陷-并行会审全部完成不合流.md) | `joinMode=ALL` 的完成条件永远为 false | 同上 |

**两个缺陷指向同一个结论：本项目的「多实例用户任务」这条路径，只有「集合来自表单字段 + 任一完成即合流」一种组合被真正验证过。**
其余组合（集合来自参与人配置、全部完成才合流）都未打通。

> ⚠️ 而开发期的冒烟测试之所以没发现，是因为它测的恰好就是"能被跑通的那一种组合"。
> **验收标准必须覆盖组合矩阵，不能只验一条路径。**
